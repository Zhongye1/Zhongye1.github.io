## 从三总线到 PCIe

第一篇里说过，CPU 和内存、外设之间靠总线通信，还分了地址总线、数据总线、控制总线。那是**共享总线**时代的模型：所有设备挂在同一组线上，谁要用谁先抢总线仲裁。这套结构简单，但频率上不去，设备一多就互相堵，插一块高速网卡可能把整条线都拖慢。

现代机器不是这么连的：

- CPU 和内存之间是**内存控制器**直连，现在这个控制器已经集成进 CPU 里了；
- CPU 和外设之间是 **PCIe** 点对点链路，每条 lane 是一对差分线，可以 x1 / x4 / x16 拼带宽。PCIe 4.0 单 lane 约 2 GB/s，x16 就是三十多 GB/s；
- 多路服务器上，CPU 之间用 UPI（Intel）或 Infinity Fabric（AMD）互连，跨路访问内存要绕一圈。

所以今天再说「总线」，更多是指**互连**，而不是一根共享的线。它带来的一个直接后果是：CPU 访问设备不再是「发个地址等结果」，而是一次跨链路的事务，延迟比访问内存高一个数量级。这也是为什么设备寄存器不会被像内存一样反复读写，通常都是攒一批操作再发。

## DMA 与 IOMMU

### MMIO：CPU 怎么控制设备

设备的控制寄存器会被映射到一段物理地址上，CPU 用普通的 load/store 就能读写，这叫 **MMIO（Memory-Mapped I/O）**。`cat /proc/iomem` 看到的那一堆区间，就是这些东西。

但这些地址不能当普通内存用：编译器可能把两次读合并成一次，CPU 也可能乱序执行，所以驱动里访问寄存器要用 `readl()` / `writel()` 这类函数，而不是直接解引用指针。`volatile` 在这里只能挡编译器，挡不住 CPU 的重排，得配合 `mb()`。

### DMA：设备怎么读写内存

反方向的数据搬运靠 **DMA（Direct Memory Access）**：网卡收到包，直接把数据写进内存，写完再发中断告诉 CPU「数据在这儿了」。整个过程 CPU 不参与搬运，只负责最后处理。

如果每个包都要 CPU 从网卡寄存器里一个字节一个字节读出来，万兆网卡一秒几百万个包，CPU 光搬数据就满了。DMA 的意义就是把这部分活交还给设备。

DMA 带来一个 Cache 一致性问题：设备绕过 CPU 直接改内存，CPU 的 Cache 里可能还是旧数据。两种处理方式：

- **一致性 DMA**：硬件保证设备写内存时会 snoop CPU Cache（x86 常见），驱动基本不用管；
- **非一致性 DMA**：需要驱动手动同步，`dma_sync_single_for_device()` / `dma_sync_single_for_cpu()` 就是在干这件事（ARM 上很常见）。

这也是为什么驱动里做 DMA 的 buffer 不能随便用栈上的变量、也不能直接传用户态指针：设备要的是**物理地址（IOVA）**，而且这块内存不能被换出、不能被迁移。

### IOMMU：给设备用的 MMU

有了 DMA，一个更麻烦的问题来了：设备能直接读写物理内存，那它凭什么只读写该读的地方？一块被直通给虚拟机的网卡，或者一个固件有问题的设备，理论上可以往内核代码段里写数据。

**IOMMU** 就是给设备用的 MMU：设备发出的 DMA 地址先经过 IOMMU 翻译和权限检查，只能落在驱动映射过的范围里。它带来三个好处：

- **隔离**：设备越权访问直接失败，而不是悄悄改坏内存；
- **虚拟化**：VFIO 把整块设备直通给虚拟机时，靠 IOMMU 保证虚拟机里的 DMA 出不了自己的地址空间；
- **大地址**：32 位设备也能 DMA 到 4GB 以上的内存（IOVA 重映射）。

检查一下自己的机器：

```sh
$ dmesg | grep -i -e DMAR -e IOMMU
$ lspci -vv | grep -i msi
```

顺带说一句，PCIe 设备的中断早就不走共享中断线了，而是 **MSI/MSI-X**：设备直接往 CPU 的中断控制器写一条消息，里面带着向量号。好处是天然支持多队列——一块多队列网卡可以申请几十个向量，每个队列一个，分别绑到不同核心上。这一点在讲软中断的时候会用到。

## 中断：从设备到 CPU

前面讲 DMA 的时候提到，设备搬完数据要发一个中断告诉 CPU。中断是设备和 CPU 之间最基础的异步通知机制，也是操作系统里最容易被低估的性能来源。

### 中断是什么？

指处理机处理程序运行中出现的紧急事件的整个过程。

程序运行过程中，系统外部、系统内部或者现行程序本身若出现紧急事件，处理机立即中止现行程序的运行，自动转入相应的处理程序（中断服务程序），待处理完后，再返回原来的程序运行，这整个过程称为程序中断。

当处理机接受中断时，只需暂停一个或几个周期而不执行处理程序的中断，称为简单中断。

中断又可分为屏蔽中断和非屏蔽中断两类。可由程序控制其屏蔽的中断称为屏蔽中断或可屏蔽中断；屏蔽时，处理机将不接受中断。反之，不能由程序控制其屏蔽、处理机一定要立即处理的中断称为非屏蔽中断或不可屏蔽中断；非屏蔽中断主要用于断电、电源故障等必须立即处理的情况。处理机响应中断时，不需执行查询程序。由被响应中断源向 CPU 发向量地址的中断称为向量中断，反之为非向量中断，向量中断可以提高中断响应速度。

### 中断是怎么送到 CPU 的

「处理机中止现行程序，转入中断服务程序」这句话背后，硬件上是有路径的：

1. 设备（网卡、磁盘、定时器）拉高自己的中断信号，或者通过 MSI 往中断控制器写一条消息；
2. 中断控制器（x86 上是 IOAPIC 加每个核的 LAPIC，ARM 上是 GIC）决定把这个中断投递给哪个 CPU 核心，并给出向量号；
3. CPU 在**当前指令执行完之后**检查中断，保存现场（至少是 CS、RIP、RFLAGS），可能还要切换内核栈；
4. 用向量号去查 **IDT（中断描述符表）**，取出对应的门描述符，跳到中断服务例程（ISR）；
5. ISR 处理完，执行 `iret` 恢复现场，回到被打断的地方继续跑。

几个值得记住的细节：

- **中断只在指令边界被响应**，不会打断一条指令的中间状态。这是很多「没加锁也没事」的代码能跑的底层原因，也是编译器可以假设单条指令原子执行的前提；
- **优先级与屏蔽**：内核可以用 `cli` 关中断，此时可屏蔽中断会挂起，但 NMI（不可屏蔽中断）照来，一般用于电源故障、硬件错误这类必须立刻处理的事件；
- **亲和性**：每个中断可以指定投递给哪个核，`/proc/irq/<号>/smp_affinity` 就是干这个的。网卡多队列时，把不同队列的中断分到不同核，才能让多个核并行收包。

### 中断合并：为什么不是越多越好

每次中断都有保存现场、跳转、恢复的开销。一个每秒几十万包的网卡，如果每个包都中断一次，CPU 光进出中断就忙不过来。所以网卡会**攒一批再发一次中断**：

```sh
$ ethtool -c eth0                    # 看中断合并参数
$ ethtool -S eth0 | grep -i queue    # 看每个队列的中断统计
```

用一点延迟换吞吐。这个延迟会直接体现在网络的尾延迟上，所以低延迟场景反而要把合并关掉。

## 软中断：中断的下半部

### 什么是软中断？

中断请求的处理程序应该要短且快，这样才能减少对正常进程运行调度的影响，而且中断处理程序可能会暂时关闭中断，这时如果中断处理程序执行时间过长，可能在还未执行完中断处理程序前，会丢失当前其他设备的中断请求。

软中断（Softirq）是一种由内核软件触发的中断机制，与硬中断不同，硬中断由外部设备发起，需要 CPU 立即响应，而软中断则在内核认为合适的时机执行，用于处理耗时但不紧急的任务。软中断通常用于完成硬中断的「下半部」工作，将复杂或耗时的处理从硬中断上下文中分离出来，以减少中断禁用时间，提高系统响应能力。

Linux 系统**为了解决中断处理程序执行过长和中断丢失的问题，将中断过程分成了两个阶段，分别是「上半部」和「下半部」**。

- **上半部用来快速处理中断**，一般会暂时关闭中断请求，主要负责处理跟硬件紧密相关或者时间敏感的事情。
- **下半部用来延迟处理上半部未完成的工作**，一般以「内核线程」的方式运行。

再举一个常见的网卡接收网络包的例子：

网卡收到网络包后，通过 DMA 方式将接收到的数据写入内存，接着会通过**硬件中断**通知内核有新的数据到了，于是内核就会调用对应的中断处理程序来处理该事件，这个事件的处理也是会分成上半部和下半部。

上半部要做的事情很少，会先禁止网卡中断，避免频繁硬中断，而降低内核的工作效率。接着，内核会触发一个**软中断**，把一些处理比较耗时且复杂的事情，交给「软中断处理程序」去做，也就是中断的下半部，其主要是需要从内存中找到网络数据，再按照网络协议栈，对网络数据进行逐层解析和处理，最后把数据送给应用程序。

所以，中断处理程序的上半部和下半部可以理解为：

- **上半部直接处理硬件请求，也就是硬中断**，主要是负责耗时短的工作，特点是快速执行；
- **下半部是由内核触发，也就是软中断**，主要是负责上半部未完成的工作，通常都是耗时比较长的事情，特点是延迟执行；

还有一个区别，硬中断（上半部）是会打断 CPU 正在执行的任务，然后立即执行中断处理程序，而软中断（下半部）是以内核线程的方式执行，并且每一个 CPU 都对应一个软中断内核线程，名字通常为「ksoftirqd/CPU 编号」，比如 0 号 CPU 对应的软中断内核线程的名字是 `ksoftirqd/0`。

不过，软中断不只是包括硬件设备中断处理程序的下半部，一些内核自定义事件也属于软中断，比如内核调度等、RCU 锁（内核里常用的一种锁）等。

### 系统里有哪些软中断？

在 Linux 系统里，我们可以通过查看 `/proc/softirqs` 的内容来知晓「软中断」的运行情况，以及 `/proc/interrupts` 的内容来知晓「硬中断」的运行情况。

![/proc/softirqs 中各类软中断的累计次数](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost3@main/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BD%AF%E4%B8%AD%E6%96%AD/softirqs.png)

可以看到，每一个 CPU 都有自己对应的不同类型软中断的**累计运行次数**，有 3 点需要注意下。

第一点，要注意第一列的内容，它是代表着软中断的类型，这里软中断包括了 10 个类型，分别对应不同的工作类型，比如 `NET_RX` 表示网络接收中断，`NET_TX` 表示网络发送中断、`TIMER` 表示定时中断、`RCU` 表示 RCU 锁中断、`SCHED` 表示内核调度中断。

第二点，要注意同一种类型的软中断在不同 CPU 的分布情况，正常情况下，同一种中断在不同 CPU 上的累计次数相差不多，这里 `NET_RX` 在 CPU0 、CPU1、CPU2、CPU3 上的中断次数基本是同一个数量级，相差不多。

第三点，这些数值是系统运行以来的累计中断次数，数值的大小没什么参考意义，但是系统的**中断次数的变化速率**才是要关注的，可以使用 `watch -d cat /proc/softirqs` 命令查看中断次数的变化速率。

前面提到过，软中断是以内核线程的方式执行的，我们可以用 `ps` 命令可以查看到，下面这个就是查到软中断内核线程的结果：

![ps 输出中的 ksoftirqd 内核线程](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost3@main/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BD%AF%E4%B8%AD%E6%96%AD/ksoftirqd.png)

可以发现，内核线程的名字外面都有中括号，这说明 ps 无法获取它们的命令行参数，所以一般来说，名字在中括号里的都可以认为是内核线程。

而且可以看到有 4 个 `ksoftirqd` 内核线程，是因为这台服务器的 CPU 是 4 核心的，每个 CPU 核心都对应着一个内核线程。

### 如何定位软中断 CPU 使用率过高的问题？

要想知道当前的系统的软中断情况，我们可以使用 `top` 命令查看，下面是一台服务器上的 top 的数据：

![top 输出中的 si 列](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost3@main/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BD%AF%E4%B8%AD%E6%96%AD/top_si.png)

上图中的黄色部分 `si`，就是 CPU 在软中断上的使用率，而且可以发现，每个 CPU 使用率都不高，其中两个 CPU 的使用率虽然只有 3% 和 4% 左右，但是都是用在软中断上了。

另外，也可以看到 CPU 使用率最高的进程也是软中断 `ksoftirqd`，因此可以认为此时系统的开销主要来源于软中断。

如果要知道是哪种软中断类型导致的，我们可以使用 `watch -d cat /proc/softirqs` 命令查看每个软中断类型的中断次数的变化速率。

![watch 观察软中断次数的变化](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost3@main/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BD%AF%E4%B8%AD%E6%96%AD/watch.png)

一般对于网络 I/O 比较高的 Web 服务器，`NET_RX` 网络接收中断的变化速率相比其他中断类型快很多。

如果发现 `NET_RX` 网络接收中断次数的变化速率过快，接下来就可以使用 `sar -n DEV` 查看网卡的网络包接收速率情况，然后分析是哪个网卡有大量的网络包进来。

![sar -n DEV 查看网卡收包速率](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost3@main/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BD%AF%E4%B8%AD%E6%96%AD/sar_dev.png)

接着，再通过 `tcpdump` 抓包，分析这些包的来源，如果是非法的地址，可以考虑加防火墙，如果是正常流量，则要考虑硬件升级等。

### 小结

为了避免由于中断处理程序执行时间过长，而影响正常进程的调度，Linux 将中断处理程序分为上半部和下半部：

- 上半部，对应硬中断，由硬件触发中断，用来快速处理中断；
- 下半部，对应软中断，由内核触发中断，用来异步处理上半部未完成的工作；

Linux 中的软中断包括网络收发、定时、调度、RCU 锁等各种类型，可以通过查看 /proc/softirqs 来观察软中断的累计中断次数情况，如果要实时查看中断次数的变化率，可以使用 watch -d cat /proc/softirqs 命令。

每一个 CPU 都有各自的软中断内核线程，可以用 ps 命令来查看内核线程，一般名字在中括号里面的，都认为是内核线程。

如果在 top 命令发现，CPU 在软中断上的使用率比较高，而且 CPU 使用率最高的进程也是软中断 ksoftirqd 的时候，这种一般可以认为系统的开销被软中断占据了。

就可以分析是哪种软中断类型导致的，一般来说都是因为网络接收软中断导致的，如果是的话，可以用 sar 命令查看是哪个网卡有大量的网络包接收，再用 tcpdump 抓网络包，做进一步分析该网络包的源头是不是非法地址，如果是就需要考虑防火墙增加规则，如果不是，则考虑硬件升级等。

## 存储设备的硬件侧

前面把 SSD 和 HDD 当成两个延时数字，其实它们的内部差得很远。

### HDD：寻道与旋转

机械硬盘的延迟由三部分组成：**寻道**（磁头移动到目标磁道）、**旋转**（等目标扇区转到磁头下面）、**传输**（真正读写）。寻道几毫秒、旋转半圈又是几毫秒，加起来就是前面说的「10 毫秒」。这也解释了为什么机械硬盘上随机读写和顺序读写能差上百倍：顺序读的时候磁头几乎不用移动。

### SSD：FTL 与写放大

固态硬盘没有机械结构，但也不是「随便写」。闪存有一个限制：**擦除必须以块为单位，写入必须以页为单位**，而且同一块不能反复擦写太多次。于是主控里跑着一层 **FTL（闪存转换层）**，把操作系统眼里的逻辑地址映射到闪存的物理页上，顺便做**磨损均衡**。

这层映射带来两个副作用：

- **写放大**：你只改了一个 4KB 的页，SSD 可能要把整个块读出来、改一个页、擦掉原块、再写回去。写放大倍数越高，寿命消耗和性能损失越大；
- **垃圾回收（GC）**：块里的有效页被搬到新块之后，旧块才能擦掉重用。GC 会和正常写入抢带宽，表现为「用久了就变慢」。

所以 SSD 会预留一部分空间（OP）专门给 GC 用，`fstrim` 则是告诉 SSD「这些块真的没用了」，让它少搬一点。

### NVMe：为闪存设计的多队列

老式 SATA 接口是给机械硬盘设计的，一条队列、深度 32。NVMe 直接跑在 PCIe 上，支持**几万条队列、每条队列几万个深度**，每个 CPU 核可以有自己的队列，天然并行。这就是为什么同代 SSD 换到 NVMe 之后，随机 IOPS 能翻好几倍——瓶颈从来不在闪存颗粒，而在接口和协议。

`perf c2c` 能直接指出哪条 Cache Line 在多个核之间来回抢（HITM，Hit Modified），也就是伪共享的现场，是最直接的定位手段。

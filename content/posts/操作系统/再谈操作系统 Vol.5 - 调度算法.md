「调度」要解决的问题是：当多个候选对象竞争同一份有限资源时，下一次应该服务谁。操作系统中有三类典型的调度：

- **进程调度**：在就绪队列中选择一个进程，把 CPU 分配给它；
- **页面置换**：物理内存已满、又发生缺页时，选择一个物理页换出，为新页面腾出位置；
- **磁盘调度**：多个磁盘 I/O 请求排队时，决定磁头先服务哪个请求，以减少寻道时间。

三者的目标并不完全相同：进程调度关注 CPU 利用率、吞吐量、周转时间、等待时间和响应时间；页面置换关注缺页率；磁盘调度关注寻道距离。但它们共享同一套权衡思路：吞吐量、公平性、响应速度和调度开销。

下面依次讨论进程调度、页面置换和磁盘调度，并在最后比较三者的共性与差异。

---

## 进程调度

进程调度算法也称 CPU 调度算法。当 CPU 空闲时，操作系统从内存中选择某个处于「就绪状态」的进程，并把 CPU 分配给它。

### 调度时机

什么时候会发生 CPU 调度？通常有以下四种情况：

1. 进程从运行状态转到等待状态；
2. 进程从运行状态转到就绪状态；
3. 进程从等待状态转到就绪状态；
4. 进程从运行状态转到终止状态。

其中，发生在第 1 和第 4 种情况下的调度称为**非抢占式调度**；发生在第 2 和第 3 种情况下的调度称为**抢占式调度**。

非抢占式的含义是：进程正在运行时，会一直运行，直到该进程完成或发生某个事件而被阻塞，才把 CPU 让给其他进程。

抢占式调度则允许正在运行的进程被打断，把 CPU 让给其他进程。抢占的原则通常有三种：时间片原则、优先权原则、短作业优先原则。

第 3 种情况也会触发 CPU 调度：假设一个进程处于等待状态，但它的优先级比较高；如果它等待的事件发生了，它就会转到就绪状态。若调度算法基于优先级，它会立即抢占正在运行的进程，于是发生 CPU 调度。

第 2 种情况通常是时间片到期：时间片到了会产生中断，从而抢占正在运行的进程。

调度算法影响的是**等待时间**，即进程在就绪队列中等待调度的时间总和；它不能影响进程真正使用 CPU 的时间和 I/O 时间。

此外，根据硬件时钟是否产生周期性中断，以及如何处理时钟中断，调度算法可以分为两类：

- **非抢占式调度算法**：挑选一个进程后，让该进程运行直到被阻塞或退出，才调用另一个进程，不理会时钟中断；
- **抢占式调度算法**：挑选一个进程后，只让它运行某段时间。时间片结束时，如果进程仍在运行，就把它挂起，调度程序从就绪队列挑选另一个进程。这种调度需要在时间间隔末端发生**时钟中断**，以便把 CPU 控制权返回给调度程序，也就是常说的**时间片机制**。

### 调度原则

调度程序需要在多个目标之间权衡。

_原则一_：如果运行的程序发生 I/O 请求，CPU 使用率会降低，因为进程正在阻塞等待硬盘数据返回。为了提高 CPU 利用率，在因 I/O 事件导致 CPU 空闲时，调度程序需要从就绪队列中选择一个进程运行。

_原则二_：有的程序执行某个任务花费的时间较长。如果它一直占用 CPU，会降低系统吞吐量，即 CPU 在单位时间内完成的进程数量。因此，调度程序要权衡长任务和短任务进程的运行完成数量。

_原则三_：进程从开始到结束包含运行时间和等待时间，两者之和称为周转时间。周转时间越小越好。如果进程等待时间很长而运行时间很短，周转时间就会被拉长，调度程序应避免这种情形。

_原则四_：就绪队列中的进程不宜等待过久。等待时间越短，进程越快进入执行。因此，就绪队列中进程的等待时间也是调度程序需要考虑的原则。

_原则五_：鼠标、键盘这类交互性强的应用，响应时间越短越好，否则会直接影响使用体验。因此，对于交互式应用，响应时间也是调度程序需要考虑的原则。

![五种调度原则](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E5%92%8C%E7%BA%BF%E7%A8%8B/23-%E4%BA%94%E7%A7%8D%E8%B0%83%E5%BA%A6%E8%A7%84%E5%88%99.jpg)

总结为五个指标：

- **CPU 利用率**：调度程序应确保 CPU 尽量处于忙碌状态；
- **系统吞吐量**：单位时间内 CPU 完成进程的数量。长作业占用 CPU 时间长，会降低吞吐量；短作业则提升吞吐量；
- **周转时间**：进程运行时间、阻塞时间和等待时间的总和，越小越好；
- **等待时间**：进程停留在就绪队列的时间，不是阻塞状态的时间；等待越久，体验越差；
- **响应时间**：用户提交请求到系统第一次产生响应所花费的时间。在交互式系统中，响应时间是衡量调度算法好坏的主要标准。

这些原则的共同目标，是让进程更快地完成，同时保持系统整体的效率与公平。

### 先来先服务调度算法

最简单的一个调度算法，是非抢占式的**先来先服务**（First Come First Served，FCFS）算法。

![FCFS 调度算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E5%92%8C%E7%BA%BF%E7%A8%8B/24-%E5%85%88%E6%9D%A5%E5%85%88%E6%9C%8D%E5%8A%A1.jpg)

顾名思义，先来后到：每次从就绪队列选择最先进入队列的进程，然后一直运行，直到进程退出或被阻塞，才会继续从队列中选择第一个进程接着运行。

这似乎很公平，但当长作业先运行时，后面的短作业等待时间会很长，不利于短作业。

FCFS 对长作业有利，适用于 CPU 繁忙型作业的系统，不适用于 I/O 繁忙型作业的系统。

### 最短作业优先调度算法

**最短作业优先**（Shortest Job First，SJF）算法优先选择运行时间最短的进程来运行，有助于提高系统吞吐量。

![SJF 调度算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E5%92%8C%E7%BA%BF%E7%A8%8B/25-%E6%9C%80%E7%9F%AD%E4%BD%9C%E4%B8%9A%E4%BC%98%E5%85%88%E7%AE%97%E6%B3%95.jpg)

这显然对长作业不利，容易造成极端现象。例如，一个长作业在就绪队列等待运行，而队列中有大量短作业，长作业会不断往后推，周转时间变长，甚至长期得不到运行。

### 高响应比优先调度算法

FCFS 和 SJF 都没有很好地权衡短作业和长作业。**高响应比优先**（Highest Response Ratio Next，HRRN）算法试图兼顾两者。

每次进行进程调度时，先计算「响应比优先级」，然后把响应比最高的进程投入运行。响应比的计算公式为：

```text
响应比 = (等待时间 + 要求服务时间) / 要求服务时间
```

从公式可以看出：

- 如果两个进程的等待时间相同，要求服务时间越短，响应比越高，短作业容易被选中；
- 如果两个进程的要求服务时间相同，等待时间越长，响应比越高，这就兼顾了长作业：随着等待时间增加，长作业的响应比会升高，最终获得运行机会。

「要求服务时间」在进程运行前无法预知。因此，高响应比优先只是一种「理想型」算法，工程上难以直接实现。

### 时间片轮转调度算法

最古老、最简单、最公平且使用最广的算法是**时间片轮转**（Round Robin，RR）调度算法。

![RR 调度算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E5%92%8C%E7%BA%BF%E7%A8%8B/27-%E6%97%B6%E9%97%B4%E7%89%87%E8%BD%AE%E8%AF%A2.jpg)

每个进程被分配一个时间段，称为**时间片**（Quantum），即允许该进程在该时间段中运行。

- 如果时间片用完，进程还在运行，就把此进程从 CPU 释放出来，把 CPU 分配给另一个进程；
- 如果进程在时间片结束前阻塞或结束，则 CPU 立即切换。

时间片长度是一个关键参数：

- 时间片太短，会导致过多的进程上下文切换，降低 CPU 效率；
- 时间片太长，短作业进程的响应时间会变长。

通常时间片设为 `20ms~50ms` 是一个比较合理的折中值。

### 最高优先级调度算法

时间片轮转算法隐含一个假设：所有进程同等重要、运行时间也一样。多用户计算机系统则希望调度有优先级，即调度程序从就绪队列中选择最高优先级的进程运行，这称为**最高优先级**（Highest Priority First，HPF）调度算法。

进程的优先级可以分为静态优先级和动态优先级：

- **静态优先级**：创建进程时确定优先级，整个运行期间不变化；
- **动态优先级**：根据进程的动态变化调整优先级。例如，进程运行时间增加则降低优先级，等待时间增加则升高优先级。

该算法有两种处理高优先级进程的方式：

- **非抢占式**：就绪队列中出现高优先级进程时，运行完当前进程，再选择高优先级进程；
- **抢占式**：就绪队列中出现高优先级进程时，当前进程挂起，调度高优先级进程运行。

缺点是可能导致低优先级进程永远不会运行。

### 多级反馈队列调度算法

**多级反馈队列**（Multilevel Feedback Queue，MFQ）调度算法是时间片轮转算法和最高优先级算法的综合与发展。

- 「多级」表示有多个队列，每个队列优先级从高到低，同时优先级越高时间片越短；
- 「反馈」表示如果有新进程加入优先级高的队列，立刻停止当前正在运行的进程，转而去运行高优先级队列。

![多级反馈队列](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E5%92%8C%E7%BA%BF%E7%A8%8B/28-%E5%A4%9A%E7%BA%A7%E9%98%9F%E5%88%97.jpg)

工作方式：

- 设置多个队列，赋予每个队列不同的优先级，优先级从高到低，优先级越高时间片越短；
- 新进程放入第一级队列末尾，按先来先服务原则排队等待调度。如果在第一级队列规定的时间片内没有运行完成，就转入第二级队列末尾，以此类推，直至完成；
- 当较高优先级队列为空，才调度较低优先级队列中的进程。如果进程运行时，有新进程进入较高优先级队列，则停止当前进程并将其移入原队列末尾，接着让较高优先级的进程运行。

对于短作业，可能在第一级队列很快处理完。对于长作业，如果在第一级队列处理不完，可以移入下一级队列等待。虽然等待时间变长，但运行时间也变长，因此该算法兼顾了长短作业，同时有较好的响应时间。

### 算法对比

| 算法 | 抢占方式     | 优点                     | 主要问题                         |
| ---- | ------------ | ------------------------ | -------------------------------- |
| FCFS | 非抢占       | 实现简单、公平           | 长作业阻塞短作业，平均等待时间长 |
| SJF  | 非抢占或抢占 | 吞吐量高，平均等待时间短 | 长作业可能饥饿；服务时间难以预知 |
| HRRN | 非抢占       | 兼顾长短作业             | 服务时间难以预知，偏理想化       |
| RR   | 抢占         | 响应时间好，适合分时系统 | 时间片过短导致切换开销大         |
| HPF  | 非抢占或抢占 | 可区分任务重要性         | 低优先级进程可能饥饿             |
| MFQ  | 抢占         | 兼顾长短作业与响应时间   | 参数多，实现复杂                 |

## 页面置换

在了解页面置换算法之前，需要先理解**缺页异常**（缺页中断）。

当 CPU 访问的页面不在物理内存时，会产生一个缺页中断，请求操作系统将所缺页面调入物理内存。缺页中断与一般中断的主要区别在于：

- 缺页中断在指令执行「期间」产生和处理中断信号，一般中断在一条指令执行「完成」后检查和处理中断信号；
- 缺页中断返回到该指令的开始重新执行「该指令」，一般中断返回到该指令的「下一条指令」执行。

![缺页中断的处理流程](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E7%BC%BA%E9%A1%B5%E5%BC%82%E5%B8%B8%E6%B5%81%E7%A8%8B.png)

缺页中断的处理流程如下：

1. CPU 执行一条 `Load M` 指令，查找 `M` 对应的页表项；
2. 如果页表项状态位为「有效」，CPU 直接访问物理内存；如果状态位为「无效」，CPU 发送缺页中断请求；
3. 操作系统收到缺页中断，执行缺页中断处理函数，先查找该页面在磁盘中的位置；
4. 找到磁盘中对应页面后，需要把页面换入物理内存。换入前，需要在物理内存中找空闲页；
5. 页面从磁盘换入物理内存后，把页表项状态位改为「有效」；
6. CPU 重新执行导致缺页异常的指令。

第 4 步是能找到空闲页的情况。如果找不到空闲页，说明内存已满，这时需要**页面置换算法**选择一个物理页：

- 如果该物理页被修改过（脏页），把它换出到磁盘；
- 把被置换出去的页表项状态改为「无效」；
- 把正在访问的页面装入这个物理页。

页表项通常包含以下字段：

![页表项字段](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E9%A1%B5%E8%A1%A8%E9%A1%B9%E5%AD%97%E6%AE%B5.png)

- **状态位**：表示该页是否有效，也就是是否在物理内存中，供程序访问时参考；
- **访问字段**：记录该页在一段时间内被访问的次数，供页面置换算法选择被淘汰页面时参考；
- **修改位**：表示该页调入内存后是否被修改过。内存中的每一页在磁盘上都有副本：如果没有修改，置换时不需要写回磁盘，可以减少开销；如果被修改过，则需要写回磁盘，以保证磁盘副本是最新的；
- **硬盘地址**：指出该页在硬盘上的地址，通常是物理块号，供调入该页时使用。

![虚拟内存的流程](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E8%99%9A%E6%8B%9F%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86%E6%B5%81%E7%A8%8B.png)

页面置换算法的功能是：**当出现缺页异常，需调入新页面而内存已满时，选择被置换的物理页面**，也就是选择一个物理页面换出到磁盘，然后把需要访问的页面换入物理页。

算法目标是尽可能减少页面的换入换出次数。常见的页面置换算法有：

- 最佳页面置换算法（OPT）
- 先进先出置换算法（FIFO）
- 最近最久未使用的置换算法（LRU）
- 时钟页面置换算法（Clock）
- 最不常用置换算法（LFU）

### 最佳页面置换算法

最佳页面置换算法（OPT）的基本思路是：**置换在未来最长时间内不会被访问的页面**。

该算法需要计算内存中每个逻辑页面的「下一次」访问时间，然后比较，选择未来最长时间不访问的页面。

![最佳页面置换算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E6%9C%80%E4%BD%B3%E7%BD%AE%E6%8D%A2%E7%AE%97%E6%B3%95.png)

这很理想，但实际系统无法实现，因为程序访问页面是动态的，无法预知每个页面在「下一次」访问前的等待时间。

因此，OPT 主要用于衡量其他算法的效率：算法效果越接近 OPT，说明算法越高效。

### 先进先出置换算法

既然无法预知页面下一次访问前的等待时间，可以选择**在内存中驻留时间最长的页面**进行置换，这就是先进先出置换（FIFO）算法的思想。

![先进先出置换算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/FIFO%E7%BD%AE%E6%8D%A2%E7%AE%97%E6%B3%95.png)

FIFO 实现简单，但没有考虑页面的访问频率。一个很早调入但仍在频繁访问的页面，可能被错误地置换出去。

### 最近最久未使用的置换算法

最近最久未使用（LRU）算法的基本思路是：发生缺页时，**选择最长时间没有被访问的页面进行置换**。该算法假设：已经很久没有使用的页面，在未来较长一段时间内仍然可能不会被使用。

LRU 近似最优置换算法：OPT 通过「未来」的使用情况推测要淘汰的页面，LRU 则通过「历史」的使用情况推测要淘汰的页面。

![最近最久未使用的置换算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/LRU%E7%BD%AE%E6%8D%A2%E7%AE%97%E6%B3%95.png)

LRU 理论上可以实现，但代价较高。完全实现 LRU 需要在内存中维护一个所有页面的链表：最近最多使用的页面在表头，最近最少使用的页面在表尾。每次访问内存都必须更新整个链表：找到页面、删除、移动到表头，操作非常耗时。

因此，LRU 虽然效果不错，但开销较大，实际应用中通常使用近似实现。

### 时钟页面置换算法

时钟页面置换算法（Clock）兼顾置换效果与实现成本，它近似 LRU，又是对 FIFO 的改进。

算法把所有页面保存在一个类似钟面的「环形链表」中，一个表针指向最老的页面。

发生缺页中断时，算法检查表针指向的页面：

- 如果访问位是 0，淘汰该页面，把新页面插入这个位置，然后把表针前移一个位置；
- 如果访问位是 1，清除访问位，把表针前移一个位置，重复这个过程，直到找到访问位为 0 的页面。

![时钟页面置换算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E6%97%B6%E9%92%9F%E7%BD%AE%E6%8D%A2%E7%AE%97%E6%B3%95.png)

由于环形链表和表针的移动方式类似时钟，该算法被称为时钟算法。

### 最不常用算法

最不常用（LFU）算法的含义是：**发生缺页中断时，选择访问次数最少的页面并将其淘汰**。

实现方式：为每个页面设置一个访问计数器，每当页面被访问时，计数器加 1；发生缺页中断时，淘汰计数器值最小的页面。

每个页面增加一个计数器看起来简单，但在操作系统中实现时需要考虑效率和硬件成本。增加计数器会增加硬件成本；查找访问次数最小的页面时，如果链表很长，查找本身也很耗时。

LFU 只考虑频率，不考虑时间。某些页面在过去访问频率很高，但现在已不再访问；当前频繁访问的页面由于累计次数还不高，可能在缺页时被错误淘汰。

一种改进方式是定期衰减访问次数：例如每次时钟中断时，把所有页面的访问次数除以 2。这样，过去的高访问次数会随时间逐渐降低，相当于提高这些页面被置换的概率。

### 算法对比

| 算法  | 淘汰依据           | 优点                   | 主要问题                         |
| ----- | ------------------ | ---------------------- | -------------------------------- |
| OPT   | 未来最长时间不访问 | 缺页率最低，理论最优   | 无法预知未来，不能实际实现       |
| FIFO  | 内存驻留时间最长   | 实现简单               | 可能淘汰仍在频繁访问的页面       |
| LRU   | 最长时间未访问     | 接近 OPT               | 维护链表开销大，通常使用近似实现 |
| Clock | 访问位与环形表针   | 开销小，近似 LRU       | 效果依赖访问位的维护             |
| LFU   | 访问次数最少       | 适合访问频率稳定的场景 | 不能反映时间变化，需要衰减机制   |

## 磁盘调度

磁盘调度算法的目的是提高磁盘的访问性能，通常通过优化磁盘访问请求的顺序来实现。

寻道时间是磁盘访问中最耗时的部分。如果请求顺序优化得当，可以节省不必要的寻道时间，从而提高磁盘访问性能。

磁盘的结构如下图所示：

![磁盘的结构](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E7%A3%81%E7%9B%98%E7%BB%93%E6%9E%84.jpg)

常见的机械磁盘中间圆的部分是磁盘的盘片，一般会有多个盘片，每个盘面都有自己的磁头。盘片中的每一层分为多个磁道，每个磁道分为多个扇区，每个扇区是 `512` 字节。多个具有相同编号的磁道形成一个圆柱，称为磁盘的柱面。

假设有如下请求序列，每个数字代表磁道的位置：

```text
98, 183, 37, 122, 14, 124, 65, 67
```

初始磁头位于第 `53` 磁道。下面分别用不同调度算法处理该序列。

### 先来先服务

先来先服务（FCFS）按照请求到达的顺序服务。

按给定序列，磁盘访问顺序为：

```text
98, 183, 37, 122, 14, 124, 65, 67
```

![先来先服务](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E7%A3%81%E7%9B%98%E8%B0%83%E5%BA%A6-%E5%85%88%E6%9D%A5%E5%85%88%E6%9C%8D%E5%8A%A1.png)

磁头总共移动了 `640` 个磁道的距离。该算法简单，但如果大量进程竞争磁盘，请求访问的磁道可能很分散，FCFS 的寻道时间会很长。

### 最短寻道时间优先

最短寻道时间优先（SSF）优先选择从当前磁头位置所需寻道时间最短的请求。

以磁头位置 53 为起点，按距离最近的请求排序，访问顺序为：

```text
65, 67, 37, 14, 98, 122, 124, 183
```

![最短寻道时间优先](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E7%A3%81%E7%9B%98%E8%B0%83%E5%BA%A6-%E6%9C%80%E7%9F%AD%E5%AF%BB%E9%81%93%E6%97%B6%E9%97%B4%E4%BC%98%E5%85%88.png)

磁头移动的总距离是 `236` 磁道，相比 FCFS 性能提高不少。

但该算法可能导致某些请求**饥饿**。如果后续请求都落在 183 磁道以内，183 磁道的请求可能永远不会被响应。产生饥饿的原因是磁头在一小块区域内来回移动。

### 扫描算法

为了避免 SSF 的饥饿问题，可以规定：**磁头在一个方向上移动，访问所有未完成的请求，直到到达磁盘在该方向上的最末端磁道，才调换方向**。这就是扫描（SCAN）算法。

该算法也称为电梯算法：电梯保持一个方向移动，直到该方向上没有请求，然后改变方向。

仍以磁头初始位置 53 为例，假设先朝磁道号减少的方向移动，访问顺序为：

```text
37, 14, 0, 65, 67, 98, 122, 124, 183
```

![扫描算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E7%A3%81%E7%9B%98%E8%B0%83%E5%BA%A6-%E6%89%AB%E6%8F%8F%E7%AE%97%E6%B3%95.png)

磁头先响应左边的请求，直到到达最左端（0 磁道）后，才开始反向移动，响应右边的请求。

SCAN 性能较好，不会产生饥饿，但中间部分的磁道会更有优势：中间部分被响应的频率高于其他部分，每个磁道的响应频率存在差异。

### 循环扫描算法

为了平衡各磁道的响应频率，可以让磁头总是按相同方向扫描。

循环扫描（C-SCAN）规定：只有磁头朝某个特定方向移动时，才处理磁道访问请求；返回时直接快速移动到最靠边缘的磁道，也就是复位磁头。返回过程很快，并且**返回中途不处理任何请求**。该算法的特点是：**磁道只响应一个方向上的请求**。

仍以磁头初始位置 53 为例，假设先朝磁道增加的方向移动，访问顺序为：

```text
65, 67, 98, 122, 124, 183, 199, 0, 14, 37
```

![循环扫描算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E7%A3%81%E7%9B%98%E8%B0%83%E5%BA%A6-C-SCAN%E7%AE%97%E6%B3%95.png)

磁头先响应右边的请求，直到碰到最右端磁道 199，立即回到磁盘开始处（磁道 0）。返回途中不响应任何请求，到达最开始的磁道后，才继续顺序响应右边的请求。

与 SCAN 相比，C-SCAN 对各位置磁道的响应频率相对更平均。

### LOOK 与 C-LOOK 算法

SCAN 和 C-SCAN 都会把磁头移动到磁盘的「最始端或最末端」才调换方向。可以进一步优化：**磁头只移动到「最远的请求」位置，然后立即反向移动**。

针对 SCAN 的优化称为 LOOK 算法：磁头在每个方向上只移动到最远的请求位置，然后立即反向移动，不需要移动到磁盘的最始端或最末端，**反向移动途中会响应请求**。

![LOOK 算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E7%A3%81%E7%9B%98%E8%B0%83%E5%BA%A6-LOOK%E7%AE%97%E6%B3%95.png)

针对 C-SCAN 的优化称为 C-LOOK：磁头在每个方向上只移动到最远的请求位置，然后立即反向移动，不需要移动到磁盘的最始端或最末端，**反向移动途中不会响应请求**。

![C-LOOK 算法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%B0%83%E5%BA%A6%E7%AE%97%E6%B3%95/%E7%A3%81%E7%9B%98%E8%B0%83%E5%BA%A6-C-LOOK%E7%AE%97%E6%B3%95.png)

### 算法对比

| 算法   | 移动策略                             | 优点                 | 主要问题               |
| ------ | ------------------------------------ | -------------------- | ---------------------- |
| FCFS   | 按请求到达顺序                       | 简单、公平           | 寻道距离可能很大       |
| SSF    | 优先最近请求                         | 平均寻道距离短       | 可能饥饿               |
| SCAN   | 单向扫描到端点再反向                 | 无饥饿，性能较好     | 中间磁道响应频率更高   |
| C-SCAN | 单向扫描到端点，快速返回且不服务     | 各磁道响应频率更均匀 | 返回路径不服务请求     |
| LOOK   | 单向移动到最远请求再反向             | 比 SCAN 少走空路     | 请求分布不均时仍有偏向 |
| C-LOOK | 单向移动到最远请求，快速返回且不服务 | 兼顾均匀性与寻道距离 | 实现相对复杂           |

## 三类调度的比较

| 调度类型 | 候选对象              | 主要目标                               | 典型算法                              |
| -------- | --------------------- | -------------------------------------- | ------------------------------------- |
| 进程调度 | 就绪队列中的进程      | CPU 利用率、吞吐量、周转时间、响应时间 | FCFS、SJF、HRRN、RR、HPF、MFQ         |
| 页面置换 | 物理内存中的页面      | 降低缺页率，减少换入换出次数           | OPT、FIFO、LRU、Clock、LFU            |
| 磁盘调度 | 等待中的磁盘 I/O 请求 | 减少寻道时间，提高磁盘吞吐量           | FCFS、SSF、SCAN、C-SCAN、LOOK、C-LOOK |

三类调度的共同点是：在资源有限、候选对象多于资源的情况下，选择一个对象先获得服务。区别在于资源类型和代价模型不同：

- 进程调度的代价主要是上下文切换，目标是让 CPU 尽量忙碌，同时保证交互响应；
- 页面置换的代价主要是磁盘 I/O，目标是减少缺页，避免频繁换入换出；
- 磁盘调度的代价主要是寻道时间，目标是让磁头移动距离更短。

算法选择没有绝对优劣，需要结合负载特征：CPU 密集型与 I/O 密集型、读多写少与写多读少、请求集中与请求分散，都会影响最终效果。

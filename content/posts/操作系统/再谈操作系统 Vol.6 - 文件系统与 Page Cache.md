文件系统是操作系统中负责管理持久数据的子系统：它把文件组织到磁盘等存储设备上，使用户可以通过路径和文件名访问数据，而不必关心数据最终落在哪些磁盘块中。

Linux 的设计原则是「一切皆文件」：普通文件、目录、块设备、管道、Socket 都交给文件系统统一管理。文件系统为每个文件维护两类核心数据结构：

- **索引节点**（inode）：记录文件的元信息和数据块位置，是文件的唯一标识；
- **目录项**（dentry）：记录文件名、inode 指针和目录层级关系，由内核维护并缓存在内存中。

在此之上，虚拟文件系统（VFS）为不同文件系统提供统一接口；文件系统负责把文件的逻辑偏移映射到磁盘块，并管理空闲空间；Page Cache 则把最近访问的文件数据缓存在内存中，减少磁盘 I/O。

下面的顺序是：先看文件系统的基本组成与 VFS，再看文件的使用方式、存储布局、空闲空间管理、文件系统结构和链接，然后讨论文件 I/O 模型，最后回到 Page Cache，回答「进程写文件时崩溃，数据会不会丢」这个问题。

## 文件系统的基本组成

文件系统的基本数据单位是文件。文件系统负责把文件存到磁盘硬件中；即使计算机断电，磁盘里的数据也不会丢失。组织方式不同，就形成不同的文件系统。

Linux 文件系统会为每个文件分配两个数据结构：**索引节点**（index node，inode）和**目录项**（directory entry，dentry），分别记录文件的元信息和目录层次结构。

- **索引节点**：记录文件的元信息，例如 inode 编号、文件大小、访问权限、创建时间、修改时间、数据在磁盘上的位置等。inode 是文件的唯一标识，一个文件对应一个 inode，inode 本身也存储在磁盘上，因此同样占用磁盘空间。
- **目录项**：记录文件名、inode 指针以及与其他目录项的层级关系。多个目录项关联起来形成目录结构。目录项由内核维护，存放在内存中，不直接存放在磁盘上。

由于 inode 唯一标识文件，而目录项记录文件名，目录项和 inode 的关系是多对一：一个文件可以有多个别名。硬链接的实现就是多个目录项中的 inode 指针指向同一个文件。

目录本身也是文件，同样由 inode 唯一标识。普通文件的磁盘块保存文件数据，目录文件的磁盘块保存子目录或文件的信息。

![目录项与索引节点的关系](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E7%9B%AE%E5%BD%95%E9%A1%B9%E5%92%8C%E7%B4%A2%E5%BC%95%E5%85%B3%E7%B3%BB%E5%9B%BE.png)

磁盘读写的最小单位是**扇区**，通常为 `512B`。如果每次读写都以扇区为单位，效率会很低。因此文件系统把多个扇区组成**逻辑块**（数据块），Linux 中常见的逻辑块大小为 `4KB`，也就是一次读写 8 个扇区。

磁盘格式化时会被划分为三个存储区域：

- **超级块**：存储文件系统的详细信息，例如块个数、块大小、空闲块等；
- **索引节点区**：存储索引节点；
- **数据块区**：存储文件或目录数据。

超级块和索引节点区不会全部常驻内存，而是在需要时加载：

- 超级块在文件系统挂载时进入内存；
- 索引节点区在文件被访问时进入内存。

## 虚拟文件系统

文件系统种类很多，操作系统希望向上层提供统一接口，于是在用户层与具体文件系统之间引入中间层：**虚拟文件系统**（Virtual File System，VFS）。

VFS 定义了一组所有文件系统都支持的数据结构和标准接口。程序员不需要了解具体文件系统的实现，只需要使用 VFS 提供的统一接口。

![虚拟文件系统](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E8%99%9A%E6%8B%9F%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F.png)

Linux 支持的文件系统按存储位置可以分为三类：

- **磁盘文件系统**：数据直接存储在磁盘中，例如 Ext2/3/4、XFS；
- **内存文件系统**：数据占用内存空间，例如 `/proc`、`/sys`，读写这些文件实际上是在读写内核中的相关数据；
- **网络文件系统**：访问其他主机上的数据，例如 NFS、SMB。

文件系统需要先挂载到某个目录才能使用。Linux 启动时会把根文件系统挂载到根目录。

## 文件的使用

从用户视角看，使用文件通常经过 `open`、`write`、`close` 等系统调用：

```c
fd = open(name, flag);   // 打开文件
write(fd, ...);          // 写数据
close(fd);               // 关闭文件
```

`open` 的参数包含文件路径和文件名；后续读写使用 `open` 返回的**文件描述符**，不再使用文件名；使用完毕后调用 `close` 关闭文件，避免资源泄漏。

打开文件后，操作系统会为每个进程维护一张**打开文件表**，表中的每一项代表一个文件描述符。文件描述符是打开文件的标识。

![打开文件表](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E6%89%93%E5%BC%80%E8%A1%A8.png)

打开文件表中维护以下状态和信息：

- **文件指针**：系统跟踪上次读写位置，作为当前文件位置指针；对打开该文件的某个进程来说，这个指针是唯一的；
- **文件打开计数器**：多个进程可能打开同一个文件，系统在删除打开文件条目之前，必须等待最后一个进程关闭文件；计数器跟踪打开和关闭的数量，计数为 0 时才删除条目；
- **文件磁盘位置**：多数文件操作需要修改文件数据，该信息保存在内存中，避免每次操作都从磁盘读取；
- **访问权限**：每个进程打开文件都需要访问模式，例如创建、只读、读写、追加；该信息保存在进程的打开文件表中，用于后续允许或拒绝 I/O 请求。

用户习惯以字节为单位读写文件，操作系统则以数据块为单位读写文件。屏蔽这种差异的工作由文件系统完成：

- 用户进程从文件读取 1 个字节时，文件系统找到该字节所在的数据块，再返回其中对应的数据部分；
- 用户进程向文件写入 1 个字节时，文件系统找到目标数据块，修改对应部分，再把数据块写回磁盘。

因此，**文件系统的基本操作单位是数据块**。

## 文件的存储

文件数据存放在磁盘上，存放方式主要分为连续空间存放和非连续空间存放。非连续空间存放又分为链表方式和索引方式。

### 连续空间存放

连续空间存放方式把文件存放在磁盘上连续的物理空间中。文件数据紧密相连，读写效率很高，因为一次磁盘寻道就可以读出整个文件。

使用连续存放的前提是预先知道文件大小，文件系统才能根据大小在磁盘上找到一块连续空间分配给文件。因此，文件头需要记录「起始块的位置」和「长度」。这里的文件头类似于 Linux 的 inode。

![连续空间存放方式](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E8%BF%9E%E7%BB%AD%E7%A9%BA%E9%97%B4%E5%AD%98%E6%94%BE%E6%96%B9%E5%BC%8F.png)

连续空间存放的缺陷是**磁盘空间碎片**和**文件长度不易扩展**：

- 删除文件后会在磁盘上留下空缺；新文件如果大于所有单个空缺，即使空缺总大小足够，也无法放入；
- 可以通过挪动现有文件腾出连续空间，但磁盘上挪动文件非常耗时。

### 非连续空间存放

非连续空间存放分为链表方式和索引方式。

#### 隐式链表

隐式链表方式下，文件头包含「第一块」和「最后一块」的位置，每个数据块中留出一个指针空间，指向下一个数据块。从链头开始顺着指针即可找到所有数据块，因此数据块可以离散存放。

![隐式链表](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E9%9D%9E%E8%BF%9E%E7%BB%AD%E7%A9%BA%E9%97%B4%E5%AD%98%E6%94%BE%E6%96%B9%E5%BC%8F-%E9%93%BE%E8%A1%A8%E6%96%B9%E5%BC%8F.png)

隐式链表的优点是消除了磁盘碎片，文件长度可以动态扩展。缺点是：

- 无法直接访问数据块，只能通过指针顺序访问；
- 每个数据块中的指针占用存储空间；
- 稳定性较差，指针丢失或损坏会导致后续文件数据无法读取。

#### 显式链接与 FAT

显式链接把用于链接文件各数据块的指针显式存放在内存的一张链接表中。整张表在磁盘上只设置一张，每个表项存放指向下一个数据块的指针。

例如，文件 A 依次使用磁盘块 4、7、2、10、12，文件 B 依次使用 6、3、11、14。从第 4 块开始顺着链走，可以找到文件 A 的全部磁盘块；从第 6 块开始可以找到文件 B 的全部磁盘块。链表以特殊标记（如 `-1`）结束。内存中的这张表称为**文件分配表**（File Allocation Table，FAT）。

![显式链接与 FAT](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E5%88%86%E9%85%8D%E8%A1%A8.png)

由于查找记录的过程在内存中进行，FAT 显著提高了检索速度，也减少了访问磁盘的次数。但整张表都存放在内存中，因此不适用于大磁盘。例如，200GB 的磁盘、1KB 的块，需要 2 亿个表项；每项 4 字节，表就占用 800MB 内存。

#### 索引方式

索引方式为每个文件创建一个**索引数据块**，其中存放指向文件数据块的指针列表。文件头包含指向索引数据块的指针，通过它可以找到索引数据块，再通过索引信息找到数据块。

创建文件时，索引块的所有指针都设为空。首次写入第 i 块时，从空闲空间取一个块，把地址写到索引块的第 i 个条目。

![索引方式](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E9%9D%9E%E8%BF%9E%E7%BB%AD%E7%A9%BA%E9%97%B4%E5%AD%98%E6%94%BE%E6%96%B9%E5%BC%8F-%E7%B4%A2%E5%BC%95%E6%96%B9%E5%BC%8F.png)

索引方式的优点是：

- 文件创建、增大、缩小方便；
- 不会产生碎片；
- 支持顺序读写和随机读写。

缺点是索引数据本身也存放在磁盘块中，小文件也需要额外分配一块索引块，带来存储开销。

如果文件很大，一个索引块放不下所有指针，可以使用组合方式：

- **链式索引块**：在索引数据块中留出指向下一个索引块的指针，索引信息用完后通过指针找到下一个索引块；缺点是某个指针损坏会导致后续数据无法读取；
- **多级索引块**：用一个索引块存放多个索引数据块的指针，一层套一层，形成多级索引。

![多级索引块](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E5%A4%9A%E7%BA%A7%E7%B4%A2%E5%BC%95%E5%9D%97.png)

### Unix 文件的实现方式

早期 Unix 文件系统组合了多种存放方式，根据文件大小选择不同策略：

- 数据块不超过 10 块时，使用直接查找；
- 超过 10 块时，使用一级间接索引；
- 一级间接索引不够时，使用二级间接索引；
- 二级间接索引也不够时，使用三级间接索引。

因此，文件头 inode 需要包含 13 个指针：

- 10 个指向数据块的指针；
- 第 11 个指向一级索引块；
- 第 12 个指向二级索引块；
- 第 13 个指向三级索引块。

![早期 Unix 文件系统的多级索引](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/Unix%20%E5%A4%9A%E7%BA%A7%E7%B4%A2%E5%BC%95.png)

这种方式对小文件和大文件都比较灵活：小文件使用直接查找，减少索引块开销；大文件使用多级索引，但访问数据块时需要多次查询。该方案用于 Linux Ext2/3 文件系统；Ext4 在此基础上做了改进。

### 存储方式对比

| 方式         | 优点                                 | 缺点                                       |
| ------------ | ------------------------------------ | ------------------------------------------ |
| 连续空间     | 顺序读写快，一次寻道可读整个文件     | 外部碎片；文件扩展困难                     |
| 隐式链表     | 无碎片，文件可动态扩展               | 只能顺序访问；指针占空间；指针损坏影响后续 |
| 显式链接 FAT | 查找在内存完成，减少磁盘访问         | FAT 表占用内存，大磁盘不适用               |
| 索引         | 支持随机访问，创建、扩展方便，无碎片 | 索引块有额外开销；大文件需要多级索引       |

## 空闲空间管理

文件存储解决的是已占用数据块的组织问题；空闲空间管理解决的是新数据块应该放在哪里。常见方法有空闲表法、空闲链表法和位图法。

### 空闲表法

空闲表法为所有空闲空间建立一张表，表项包括空闲区的第一个块号和该空闲区的块个数。该方式适用于连续分配。

请求分配磁盘空间时，系统依次扫描空闲表，直到找到合适的空闲区域；撤销文件时，系统回收文件空间，顺序扫描空闲表，把释放空间的第一个物理块号及块数填入条目。

空闲表法仅在空闲区较少时效果较好。如果存在大量小空闲区，空闲表会变得很大，查询效率降低。该方式适用于建立连续文件。

![空闲表法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E7%A9%BA%E9%97%B2%E8%A1%A8%E6%B3%95.png)

### 空闲链表法

空闲链表法在每个空闲块中放一个指针，指向下一个空闲块。创建文件需要空闲块时，从链头依次取下；回收空间时，把空闲块依次接到链头。

该方法只需在主存中保存一个指向第一个空闲块的指针，实现简单；但不能随机访问，工作效率较低，因为增加或移动空闲块需要多次 I/O，指针也占用存储空间。空闲表法和空闲链表法都不适合大型文件系统。

![空闲链表法](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E7%A9%BA%E9%97%B2%E5%9D%97%E9%93%BE%E8%A1%A8.png)

### 位图法

位图法用二进制的一位表示一个磁盘块的使用情况。磁盘上所有盘块都有一个二进制位与之对应：`0` 表示空闲，`1` 表示已分配。

```text
1111110011111110001110110111111100111 ...
```

Linux 文件系统采用位图管理空闲空间，既用于数据块，也用于 inode，因为 inode 同样存储在磁盘上，也需要管理。

## 文件系统的结构

Linux 用位图管理空闲空间。创建新文件时，内核通过 inode 位图找到空闲 inode 并分配；存储数据时，通过块位图找到空闲块并分配。

数据块位图本身也放在磁盘块中。假设一个块为 4KB，每一位表示一个数据块，则一个块可以表示 `4 × 1024 × 8 = 2^15` 个空闲块；每个数据块 4KB，最大可表示 `2^15 × 4 × 1024 = 2^27` 字节，即 128MB。

如果只使用「一个块的位图 + 一系列块」以及「一个块的 inode 位图 + 一系列 inode」，最大只能表示 128MB，远远不够。Linux 文件系统把这种结构称为一个**块组**，多个块组可以表示更大的文件系统。

![块组结构](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E5%9D%97%E7%BB%84.png)

Linux Ext2 文件系统由大量块组组成，在硬盘上相继排布。最前面是引导块，用于系统启动时引导；之后是连续的块组。块组内容包括：

- **超级块**：文件系统的重要信息，例如 inode 总个数、块总个数、每个块组的 inode 个数和块个数；
- **块组描述符**：记录文件系统中各个块组的状态，例如空闲块和 inode 数目；每个块组都包含所有块组的描述符信息；
- **数据位图和 inode 位图**：表示对应数据块或 inode 是否空闲；
- **inode 列表**：包含块组中所有 inode，保存文件或目录的元数据；
- **数据块**：保存文件数据。

每个块组都重复保存超级块和块组描述符，原因有两个：

- 如果系统崩溃破坏超级块或块组描述符，文件系统结构和内容信息可能全部丢失；冗余副本可以用于恢复；
- 让文件管理数据尽可能接近，减少磁头寻道和旋转，提高文件系统性能。

Ext2 的后续版本采用稀疏技术：超级块和块组描述符不再存放到每个块组，而是只写入块组 0、块组 1 以及编号为 3、5、7 的幂的块组。

### 目录的存储

目录也是文件，同样有 inode，inode 指向一些块。普通文件的块保存文件数据，目录文件的块保存目录项信息。

最简单的目录格式是**列表**：把目录下的文件名、inode、文件类型等信息逐项列在表中。每一项代表该目录下文件的文件名和对应 inode，通过 inode 可以找到真正的文件。

通常第一项是 `.`，表示当前目录；第二项是 `..`，表示上一级目录；之后是文件名和 inode。

如果目录下文件很多，逐项查找效率会很低。因此目录格式可以改为**哈希表**：对文件名计算哈希值并保存，查找时通过名称取哈希，匹配后即可定位文件信息所在的块。Linux Ext 文件系统采用哈希表保存目录内容，查找迅速，插入和删除也较简单，但需要处理哈希冲突。

![目录格式与哈希表](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E7%9B%AE%E5%BD%95%E5%93%88%E5%B8%8C%E8%A1%A8.png)

目录查询需要在磁盘上反复搜索，I/O 开销较大。为了减少 I/O，内核会把当前使用的目录缓存在内存中；后续访问同一目录时直接在内存中操作，从而降低磁盘访问次数。

## 软链接与硬链接

Linux 可以通过**硬链接**（Hard Link）和**软链接**（Symbolic Link）为文件创建别名。两者都是特殊文件，但实现方式不同。

### 硬链接

硬链接是多个目录项中的 inode 指向同一个文件，也就是指向同一个 inode。inode 不能跨文件系统，因为每个文件系统都有各自的 inode 数据结构和列表，所以硬链接不能跨文件系统。

由于多个目录项指向同一个 inode，只有删除文件的所有硬链接以及源文件时，系统才会彻底删除该文件。

![硬链接](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E7%A1%AC%E9%93%BE%E6%8E%A5-2.png)

### 软链接

软链接相当于重新创建一个文件，这个文件有独立的 inode，但文件内容是另外一个文件的路径。访问软链接时，实际访问的是目标文件。

软链接可以跨文件系统；目标文件被删除后，链接文件仍然存在，只是指向的文件已经找不到。

![软链接](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%96%87%E4%BB%B6%E7%B3%BB%E7%BB%9F/%E8%BD%AF%E9%93%BE%E6%8E%A5.png)

## 文件 I/O

文件 I/O 可以按不同维度分类：缓冲与非缓冲、直接与非直接、阻塞与非阻塞、同步与异步。

### 缓冲与非缓冲 I/O

根据是否利用标准库缓冲，文件 I/O 可以分为：

- **缓冲 I/O**：利用标准库缓存加速文件访问，标准库再通过系统调用访问文件；
- **非缓冲 I/O**：直接通过系统调用访问文件，不经过标准库缓存。

这里的「缓冲」特指标准库内部实现的缓冲。例如，很多程序遇到换行才真正输出，换行前的内容被标准库暂时缓存，以减少系统调用次数。系统调用本身存在 CPU 上下文切换开销。

### 直接与非直接 I/O

磁盘 I/O 很慢，Linux 内核为了减少磁盘 I/O 次数，会在系统调用后把用户数据拷贝到内核缓存，也就是**页缓存**；只有缓存满足某些条件时，才发起磁盘 I/O。

根据是否利用操作系统的缓存，文件 I/O 可以分为：

- **直接 I/O**：不发生内核缓存与用户程序之间的数据复制，直接经过文件系统访问磁盘；
- **非直接 I/O**：读操作时，数据从内核缓存拷贝给用户程序；写操作时，数据从用户程序拷贝到内核缓存，再由内核决定何时写入磁盘。

使用文件操作类系统调用时，指定 `O_DIRECT` 标志表示直接 I/O；未设置时默认使用非直接 I/O。

非直接 I/O 写数据时，以下场景会触发内核缓存写入磁盘：

- `write` 结束时，内核缓存的数据太多；
- 用户主动调用 `sync`；
- 内存紧张，无法再分配页面；
- 内核缓存的数据超过某个时间阈值。

### 阻塞与非阻塞 I/O

**阻塞 I/O**：用户程序执行 `read` 时，线程被阻塞，直到内核数据准备好，并把数据从内核缓冲区拷贝到应用程序缓冲区，`read` 才返回。

阻塞等待包含两个过程：

1. 内核数据准备好；
2. 数据从内核态拷贝到用户态。

**非阻塞 I/O**：`read` 请求在数据未准备好时立即返回，应用程序可以继续执行；之后不断轮询内核，直到数据准备好，内核把数据拷贝到应用程序缓冲区，`read` 才获取到结果。

最后一次 `read` 获取数据的过程仍然是同步的，需要等待内核态数据拷贝到用户程序缓冲区。

访问管道或 Socket 时，设置 `O_NONBLOCK` 标志表示非阻塞 I/O；不做设置时默认是阻塞 I/O。

轮询会浪费 CPU。**I/O 多路复用**技术通过 `select`、`poll` 等机制进行 I/O 事件分发：内核数据准备好时，以事件通知应用程序。调用 I/O 多路复用接口后，如果没有事件发生，当前线程会阻塞，CPU 可以切换去执行其他线程；内核发现事件到来时唤醒阻塞线程。

I/O 多路复用的优势是：一个线程可以同时处理多个 Socket 的 I/O 请求。应用程序注册多个 Socket，不断调用 I/O 多路复用接口读取被激活的 Socket，就可以在同一个线程内处理多个 I/O 请求。同步阻塞模型则必须通过多线程才能达到同样目的。

需要注意，I/O 多路复用在 `read` 获取数据时，数据从内核态拷贝到用户态的过程仍然是同步的，需要等待。

### 同步与异步 I/O

阻塞 I/O、非阻塞 I/O、基于非阻塞 I/O 的多路复用都属于**同步调用**：`read` 调用时，内核把数据从内核空间拷贝到应用程序空间，这个过程需要等待；如果内核拷贝效率不高，`read` 会在同步过程中等待较长时间。

真正的**异步 I/O** 中，「内核数据准备好」和「数据从内核态拷贝到用户态」两个过程都不需要等待。发起 `aio_read` 后立即返回，内核自动把数据从内核空间拷贝到应用程序空间，拷贝过程由内核完成，应用程序不需要主动发起拷贝。

| 模型         | 数据准备阶段 | 数据拷贝阶段 | 是否同步 |
| ------------ | ------------ | ------------ | -------- |
| 阻塞 I/O     | 阻塞         | 阻塞         | 同步     |
| 非阻塞 I/O   | 轮询         | 阻塞         | 同步     |
| I/O 多路复用 | 阻塞在事件   | 阻塞         | 同步     |
| 异步 I/O     | 不阻塞       | 不阻塞       | 异步     |

## Page Cache 与文件持久化

Page Cache 的淘汰策略、预读失效与缓存污染等工程问题在 Vol.2 内存管理篇已有讨论；本节侧重 Page Cache 的组成、与 buffer cache 的关系，以及文件持久化与一致性。

一个常见问题是：进程使用缓冲 I/O 写文件，写到一半时进程崩溃，已经写入的数据是否会丢失。

答案是不会。进程执行 `write` 系统调用时，数据被写入内核的 **Page Cache**。Page Cache 是文件系统用于缓存文件数据的内存区域。即使进程崩溃，文件数据仍保留在内核的 Page Cache 中；后续读取也会优先从 Page Cache 读取，因此仍能读到进程崩溃前写入的数据。

内核会在合适的时机把 Page Cache 中的数据持久化到磁盘。如果 Page Cache 中的文件数据在持久化到磁盘之前系统发生崩溃，这部分数据就会丢失。程序可以调用 `fsync`，在写文件时立刻把文件数据持久化到磁盘，以避免系统崩溃导致的数据丢失。

### Page Cache 是什么

Linux 的文件 I/O 系统中，Page Cache 是由内核管理的内存区域。通过 `mmap` 以及缓冲 I/O 把文件读取到内存空间，实际上都是读取到 Page Cache 中。

![Page Cache 在文件 I/O 中的位置](https://cdn.xiaolincoding.com//mysql/other/72568a29816fa9b505f15edac68adee2.png)

`page` 是内存管理分配的基本单位，Page Cache 由多个 page 构成。page 在操作系统中通常为 `4KB`，Page Cache 的大小为 4KB 的整数倍。并不是所有 page 都被组织为 Page Cache。

Linux 中用户可访问的内存分为两类：

- **File-backed pages**：文件备份页，也就是 Page Cache 中的 page，对应磁盘上的若干数据块；主要问题是脏页回盘；
- **Anonymous pages**：匿名页，不对应磁盘上的任何数据块，例如进程的栈、局部变量等。

Linux 不把 Page Cache 称为 block cache，是因为从磁盘加载到内存的数据不仅放在 Page Cache 中，还可能放在 buffer cache 中。通过 Direct I/O 读取的磁盘文件就不会进入 Page Cache。

### 查看 Page Cache

读取 `/proc/meminfo` 可以获取系统内存情况：

```shell
$ cat /proc/meminfo
...
Buffers:            1224 kB
Cached:           111472 kB
SwapCached:        36364 kB
Active:          6224232 kB
Inactive:         979432 kB
Active(anon):    6173036 kB
Inactive(anon):   927932 kB
Active(file):      51196 kB
Inactive(file):    51500 kB
...
Shmem:             10000 kB
...
SReclaimable:      43532 kB
...
```

根据这些数据，可以得出：

```text
Buffers + Cached + SwapCached = Active(file) + Inactive(file) + Shmem + SwapCached
Page Cache = Buffers + Cached + SwapCached
```

执行 `free` 命令时，`buffers` 和 `cached` 两列也与 Page Cache 有关：

```text
~ free -m
             total       used       free     shared    buffers     cached
Mem:        128956      96440      32515          0       5368      39900
-/+ buffers/cache:      51172      77784
Swap:        16002          0      16001
```

`cached` 表示当前页缓存占用量，`buffers` 表示当前块缓存占用量。

### Swap 与缺页中断

Swap 机制在物理内存不够用时回收内存空间：操作系统以 page 为单位管理内存，把不常用的页换出到磁盘，为新的内存申请让出位置。进程访问不在内存中的页时触发**缺页中断**，操作系统再把页读回内存。

File-backed pages（Page Cache）的回收代价较低：它们通常对应文件上的若干顺序块，可以通过顺序 I/O 落盘；如果页上没有写操作、没有脏页，甚至可以不回盘，因为数据可以通过再次读取磁盘文件得到。

Anonymous pages 的回收代价较高：它们通常随机写入交换设备；无论是否有写操作，为了保证数据不丢失，swap 时都必须持久化到磁盘。

Linux 通过 `swappiness` 参数（取值 0-100）控制 swap 的倾向：数值越高，越积极地换出不活跃页；数值越低，越少进行 swap，以避免交互式应用因频繁换页而增加响应延迟。

`SwapCached` 也属于 Page Cache：匿名页被 swap out 到磁盘后，再 swap in 回内存时，原来的 Swap File 仍然存在，因此这部分页可以看作 File-backed page。Swap 的完整机制在 Vol.2 内存管理篇已经展开，这里只补充它与 Page Cache 的关系。

### Page Cache 与 buffer cache

一句话概括：**Page Cache 用于缓存文件的页数据，buffer cache 用于缓存块设备（如磁盘）的块数据。**

- 页是逻辑上的概念，Page Cache 与文件系统同级；
- 块是物理上的概念，buffer cache 与块设备驱动程序同级。

两者的共同目的都是加速数据 I/O：

- 写数据时先写到缓存，把写入的页标记为 dirty，然后向外部存储 flush；这是缓存写机制中的 write-back，Linux 默认不采用 write-through；
- 读数据时先读缓存，未命中再去外部存储读取，并把读取的数据加入缓存。操作系统会尽量把所有空闲内存用作 Page Cache 和 buffer cache，内存不够时用 LRU 等算法淘汰缓存页。

Linux 2.4 之前，Page Cache 与 buffer cache 完全分离。块设备大多是磁盘，磁盘数据又大多通过文件系统组织，这种设计导致很多数据被缓存两次，浪费内存。

Linux 2.4 之后，两块缓存近似融合：如果一个文件的页加载到了 Page Cache，buffer cache 只需要维护块指向页的指针。只有没有文件表示的块，或者绕过文件系统直接操作的块（例如 `dd` 命令），才会真正放到 buffer cache 中。

因此，现在提到 Page Cache，通常同时指 Page Cache 和 buffer cache 两者，后续不再区分。

Page Cache 中的每个文件都是一棵基数树（radix tree，本质上是多叉搜索树），树的每个节点是一个页。根据文件内偏移量可以快速定位到所在的页。

### 预读机制

操作系统为基于 Page Cache 的读缓存提供**预读机制**（PAGE_READAHEAD）。例如：

- 用户线程请求读取磁盘文件 A 的 offset `0-3KB` 范围内的数据，磁盘基本读写单位为 block（4KB），操作系统至少会读取 `0-4KB` 的内容，正好可以放在一个 page 中；
- 操作系统基于局部性原理，还会把 `[4KB,8KB)`、`[8KB,12KB)`、`[12KB,16KB)` 的磁盘块加载到内存，额外申请 3 个 page。

![Page Cache 预读机制](https://cdn.xiaolincoding.com//mysql/other/ae8252378169c8c14b8b9907983f7d8b-20230309235145646.png)

应用程序用 `read` 读取 4KB 数据时，内核实际上通过 readahead 完成了 16KB 数据的读取。

### 一致性与持久化

任何系统引入缓存，都会引发一致性问题：内存中的数据与磁盘中的数据可能不一致。

**文件 = 数据 + 元数据**。元数据描述文件的各种属性，也必须存储在磁盘上。因此，保证文件一致性包含数据一致和元数据一致两个方面。元数据包括文件大小、创建时间、访问时间、属主属组等。

如果写操作对应的数据在 Page Cache 中，写操作会直接作用于 Page Cache。如果数据还没刷新到磁盘，内存中的数据就领先于磁盘，此时对应的 page 称为 **Dirty page**。

Linux 下有两种实现文件一致性的方式：

1. **Write Through（写穿）**：向用户层提供特定接口，应用程序可以主动调用接口保证文件一致性；
2. **Write Back（写回）**：系统中存在定期任务（内核线程），周期性同步文件系统中的脏数据块，这是 Linux 默认的一致性方案。

两种方式最终都依赖系统调用，主要有三种：

| 方法            | 含义                                                                                                                                             |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `fsync(fd)`     | 将 fd 代表的文件的脏数据和脏元数据全部刷新至磁盘                                                                                                 |
| `fdatasync(fd)` | 将 fd 代表的文件的脏数据刷新至磁盘，同时刷新必要的元数据；必要元数据指对后续访问文件有关键作用的信息，例如文件大小，文件修改时间等不属于必要信息 |
| `sync()`        | 将系统中所有脏的文件数据和元数据刷新至磁盘                                                                                                       |

Write Through 与 Write Back 在持久化可靠性上有所不同：

- Write Through 以牺牲系统 I/O 吞吐量为代价，向上层应用确保一旦写入，数据就已经落盘，不会丢失；
- Write Back 在系统宕机时无法确保数据已经落盘，因此存在数据丢失问题。不过，如果只是程序崩溃，例如被 `kill -9`，Page Cache 中的数据操作系统仍会确保落盘。

### Page Cache 的优劣势

**优势：**

- **加快数据访问**：数据在内存中缓存，下一次访问直接命中内存，不需要磁盘 I/O；
- **减少 I/O 次数，提高吞吐量**：Page Cache 的缓存和预读能力配合程序局部性，一次 I/O 可以把多个 page 装入缓存，减少磁盘 I/O 次数。

**劣势：**

- 需要占用额外物理内存；内存紧张时可能导致频繁 swap，最终提高磁盘 I/O 负载；
- 对应用层没有很好的管理 API，几乎是透明管理；应用层即使想优化 Page Cache 使用策略也很难，因此一些应用选择在用户空间实现自己的 page 管理，例如 MySQL InnoDB 以 16KB 的页进行管理；
- 在某些场景下比 Direct I/O 多一次磁盘读 I/O 和磁盘写 I/O。

### Direct I/O

Direct I/O 即直接 I/O。名字中的「直接」用于区分使用 Page Cache 机制的缓存 I/O：

- **缓存文件 I/O**：用户空间读写文件不直接与磁盘交互，中间夹了一层 Page Cache；
- **直接文件 I/O**：用户空间读取的文件直接与磁盘交互，没有中间 Page Cache 层。

Direct I/O 还有另一层语义：其他技术中数据至少需要在内核空间存储一份，而 Direct I/O 中数据直接存储在用户空间，绕过了内核。

Direct I/O 的读写特点：

- **Write 操作**：不使用 Page Cache，写文件返回成功时，数据已经落盘（不考虑磁盘自带缓存）；
- **Read 操作**：不使用 Page Cache，每次读操作都真正从磁盘读取，不会从文件系统缓存中读取。

### TD

进程崩溃与系统崩溃对已写入数据的影响不同：

- 进程调用 `write` 后崩溃：数据已在内核 Page Cache 中，进程崩溃不会清空内核缓存，数据通常不会丢失；
- 系统在 Page Cache 刷盘前崩溃：Page Cache 中的数据会丢失；
- 调用 `fsync` 后：数据和必要的元数据已刷新到磁盘，可以避免系统崩溃导致的数据丢失。

Page Cache 提高了读性能和写吞吐量，但以占用内存和引入一致性问题为代价；Direct I/O 则绕过 Page Cache，把数据直接写入磁盘或从磁盘读取。

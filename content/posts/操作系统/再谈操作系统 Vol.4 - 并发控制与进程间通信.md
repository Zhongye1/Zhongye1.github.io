多个执行单元并发运行时，如果同时访问共享资源，就可能产生竞态条件：最终结果取决于调度顺序，每次运行都可能不同。解决这类问题需要两种机制：

- **互斥**：保证临界区在任意时刻只有一个执行流进入；
- **同步**：规定多个执行流之间的先后顺序，例如生产者先生产、消费者后消费。

实现互斥与同步的基本手段是**锁**和**信号量**。锁适合保护一段临界区；信号量既能实现互斥，也能实现事件同步。围绕它们，还有生产者-消费者、哲学家就餐、读者-写者等经典问题。使用不当则会引入**死锁**：多个执行流互相等待对方持有的资源，谁也无法继续。

另一条线是**进程间通信**。每个进程的用户地址空间彼此独立，不能直接访问对方的数据；内核空间由所有进程共享，因此进程间通信必须经过内核。Linux 提供了管道、消息队列、共享内存、信号量、信号和 Socket 等机制，它们在数据格式、拷贝次数、通信范围和适用场景上各有取舍。

下面先讨论竞争、互斥与同步，再依次展开锁、信号量与经典同步问题、死锁，最后梳理各类进程间通信机制。

## 竞争、互斥与同步

在单核 CPU 系统中，为了实现多个程序同时运行的假象，操作系统通常以时间片调度的方式，让每个进程每次执行一个时间片，时间片用完后切换下一个进程。由于时间片很短，于是产生了「并发」的现象。

![并发](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/3-%E5%B9%B6%E5%8F%91.jpg)

另外，操作系统也为每个进程创建巨大、私有的虚拟内存假象，这种地址空间抽象让每个程序好像拥有自己的内存，而实际上操作系统在背后让多个地址空间「复用」物理内存或者磁盘。

![虚拟内存管理-换入换出](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/4-%E5%86%85%E5%AD%98%E4%BA%A4%E6%8D%A2.jpg)

如果一个程序只有一个执行流程，它就是单线程的。一个程序也可以有多个执行流程，也就是多线程程序。线程是调度的基本单位，进程则是资源分配的基本单位。

所以，线程之间可以共享进程的资源，比如代码段、堆空间、数据段、打开的文件等，但每个线程都有自己独立的栈空间。

![多线程](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/5-%E5%A4%9A%E7%BA%BF%E7%A8%8B.jpg)

多个线程如果竞争共享资源，且没有采取有效保护措施，就会造成共享数据混乱。

### 竞态条件

用两个线程分别对共享变量 `i` 自增 `1`，各执行 `10000` 次：

```c
int i = 0;

void *thread1(void *arg) {
    for (int n = 0; n < 10000; n++) {
        i++;
    }
    return NULL;
}

void *thread2(void *arg) {
    for (int n = 0; n < 10000; n++) {
        i++;
    }
    return NULL;
}
```

按预期，`i` 的最终值应为 `20000`。实际运行时，结果可能是 `15173`，也可能是 `20000`，每次都可能不同。这种结果取决于调度顺序、无法预先确定的现象，称为**竞争条件**（race condition）。

原因在于，`i++` 在 CPU 上并不是一条指令，而是三条：

1. 从内存读取 `i` 到寄存器；
2. 寄存器中的值加 1；
3. 将寄存器中的值写回内存。

假设 `i` 当前为 50，线程 1 执行到第 2 步后发生时钟中断，操作系统把线程 1 的状态保存到线程控制块 TCB。线程 2 被调度运行，也从内存读到 50，并完成加 1 和写回，此时内存中的 `i` 变为 51。随后线程 1 恢复执行，它寄存器中的值仍是 51，再写回内存，`i` 依然是 51。

两次自增只产生了一次效果。根本原因是**读、改、写三个步骤不是原子操作**，中间可能被调度打断。

### 临界区与互斥

多线程执行操作共享变量的这段代码，可能导致竞争状态，因此称为**临界区**（critical section）。临界区是访问共享资源的代码片段，不能由多个线程同时执行。

希望这段代码具有**互斥性**（mutual exclusion）：一个线程在临界区执行时，其他线程应被阻止进入临界区。也就是说，这段代码执行过程中，最多只能出现一个线程。

![互斥](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/10-%E4%B8%B4%E7%95%8C%E5%8C%BA.jpg)

互斥并不只针对多线程。在多进程竞争共享资源时，同样可以使用互斥方式避免资源竞争造成的数据混乱。

### 同步

互斥解决了并发进程或线程对临界区的使用问题。这种基于临界区控制的交互比较简单：只要一个进程或线程进入临界区，其他试图进入的进程或线程都会被阻塞，直到第一个离开临界区。

但多线程并不一定顺序执行，它们以各自独立、不可预知的速度推进。有时又希望多个线程密切合作，完成一个共同任务。

例如，线程 1 负责读入数据，线程 2 负责处理数据。线程 2 在没有收到线程 1 的唤醒通知时，会一直阻塞等待；线程 1 读完数据并把数据传给线程 2 时，会唤醒线程 2。

**同步**指的是：并发进程或线程在一些关键点上可能需要互相等待与互通消息，这种相互制约的等待与互通信息称为进程或线程同步。

同步与互斥是两个不同的概念：

- 同步描述顺序关系，例如「操作 A 应在操作 B 之前执行」「操作 C 必须在操作 A 和操作 B 都完成之后才能执行」；
- 互斥描述排他关系，例如「操作 A 和操作 B 不能在同一时刻执行」。

## 锁

实现互斥与同步的两种主要方法是**锁**和**信号量**。锁提供加锁、解锁操作；信号量提供 P、V 操作。两者都可以实现互斥，而信号量还能方便地实现同步。

### 忙等待锁与自旋锁

任何想进入临界区的线程，必须先执行加锁操作。加锁成功后才能进入临界区；完成对临界资源的访问后，再执行解锁操作，释放临界资源。

![加锁-解锁](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/12-%E4%BA%92%E6%96%A5%E9%94%81.jpg)

根据实现方式不同，锁可以分为「忙等待锁」和「无忙等待锁」。

现代 CPU 提供特殊的原子操作指令——**测试和置位**（Test-and-Set）。用 C 代码表示其行为：

```c
bool TestAndSet(bool *old_ptr, bool new_value) {
    bool old = *old_ptr;
    *old_ptr = new_value;
    return old;
}
```

这段逻辑做两件事：

- 把 `old_ptr` 更新为 `new_value`；
- 返回 `old_ptr` 的旧值。

关键在于，这两步原子执行，不会被中断拆开。**原子操作**要么全部执行，要么都不执行，不会出现执行到一半的中间状态。

利用 Test-and-Set 可以实现忙等待锁：

```c
bool flag = false;

void lock() {
    while (TestAndSet(&flag, true)) {
        // 锁已被占用，继续自旋
    }
}

void unlock() {
    flag = false;
}
```

工作过程分两种情况：

- 没有其他线程持有锁时，`flag` 为 0。调用 `TestAndSet(flag, 1)` 返回 0，线程跳出循环并获得锁，同时原子地把 `flag` 设为 1；
- 锁已被其他线程持有时，`TestAndSet(flag, 1)` 返回 1。只要对方不释放锁，本线程会一直循环等待。当 `flag` 被改为 0 后，本线程再次调用 `TestAndSet`，返回 0 并原子地设为 1，从而获得锁。

获取不到锁时，线程一直执行 `while` 循环，不做其他事情，因此称为「忙等待锁」，也称为**自旋锁**（spin lock）。

自旋锁是最简单的一种锁：一直自旋，利用 CPU 周期，直到锁可用。在单处理器上，需要抢占式调度器，即不断通过时钟中断切换线程；否则，自旋锁在单 CPU 上无法使用，因为一个自旋的线程永远不会主动放弃 CPU。

### 无忙等待锁

无等待锁在获取不到锁时不自旋，而是把当前线程放入锁的等待队列，然后执行调度程序，把 CPU 让给其他线程执行。

![无等待锁](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/15-%E6%97%A0%E7%AD%89%E5%BE%85%E9%94%81.jpg)

具体实现会更复杂，但基本元素仍是「检查锁状态」与「把线程挂起或唤醒」。

### 互斥锁与自旋锁

互斥锁和自旋锁是最底层的两种锁，许多高级锁都基于它们实现。加锁的目的都是保证共享资源在任意时刻只有一个线程访问；区别在于加锁失败后的处理方式：

- **互斥锁**加锁失败后，线程释放 CPU，给其他线程；
- **自旋锁**加锁失败后，线程忙等待，直到拿到锁。

互斥锁是一种独占锁。线程 A 加锁成功后，互斥锁被 A 独占；只要 A 没有释放，线程 B 加锁就会失败，于是 B 释放 CPU，加锁代码被阻塞。

互斥锁加锁失败而阻塞的现象由操作系统内核实现。加锁失败时，内核把线程置为「睡眠」状态，等到锁被释放后，再在合适的时机唤醒线程。这个过程包含**两次线程上下文切换**：

- 加锁失败时，内核把线程从「运行」状态改为「睡眠」状态，把 CPU 切换给其他线程；
- 锁被释放后，睡眠线程变为「就绪」状态，内核在合适的时间把 CPU 切换给该线程。

线程上下文切换的耗时通常在几十纳秒到几微秒之间。如果锁住的代码执行时间很短，上下文切换的时间可能比代码本身还长。

因此，如果能确定被锁住的代码执行时间很短，应选用自旋锁；否则使用互斥锁。

自旋锁通过 CPU 提供的 `CAS` 函数（Compare And Swap）在用户态完成加锁和解锁，不会主动产生线程上下文切换，因此比互斥锁快一些，开销也小一些。

一般加锁包含两个步骤：

- 查看锁的状态，如果锁空闲，则继续；
- 将锁设置为当前线程持有。

CAS 把这两个步骤合并成一条硬件级原子指令，保证不可分割。例如，设锁为变量 `lock`，0 表示空闲，线程 ID 表示持有者，则 `CAS(lock, 0, pid)` 表示加锁，`CAS(lock, pid, 0)` 表示解锁。

自旋锁在竞争发生时忙等待，可以用 `while` 循环实现，也可以使用 CPU 提供的 `PAUSE` 指令，以减少循环等待时的耗电量。

自旋锁适合异步、协程等在用户态切换请求的编程方式；如果被锁住的代码执行时间过长，自旋线程会长时间占用 CPU，因此自旋时间与被锁代码执行时间成正比。

### 读写锁

读写锁由「读锁」和「写锁」两部分构成：只读取共享资源时用读锁，修改共享资源时用写锁。它适用于能明确区分读操作和写操作的场景。

工作原理：

- 写锁没有被线程持有时，多个线程可以并发持有读锁。读锁用于读取共享资源，多个线程同时持有不会破坏数据；
- 一旦写锁被线程持有，读线程获取读锁的操作会被阻塞，其他写线程获取写锁的操作也会被阻塞。

因此，写锁是独占锁，任何时刻只能有一个线程持有；读锁是共享锁，可以被多个线程同时持有。读写锁在读多写少的场景能发挥优势。

根据实现不同，读写锁可以分为「读优先锁」和「写优先锁」。

读优先锁期望读锁能被更多线程持有，以提高读线程的并发性。工作方式：读线程 A 先持有读锁，写线程 B 获取写锁时被阻塞；在 B 阻塞期间，后续读线程 C 仍然可以成功获取读锁；直到 A 和 C 都释放读锁，B 才能获取写锁。

写优先锁优先服务写线程。工作方式：读线程 A 先持有读锁，写线程 B 获取写锁时被阻塞；在 B 阻塞期间，后续读线程 C 获取读锁会失败并被阻塞；只要 A 释放读锁，B 就可以获取写锁。

读优先锁对读线程并发性更好，但如果一直有读线程获取读锁，写线程会永远获取不到写锁，造成写线程「饥饿」。写优先锁保证写线程不会饿死，但如果一直有写线程获取写锁，读线程也会被「饿死」。

为了避免饥饿，可以使用「公平读写锁」：用队列把获取锁的线程排队，读线程和写线程都按先进先出原则加锁。这样读线程仍然可以并发，也不会出现饥饿现象。

### 悲观锁与乐观锁

互斥锁、自旋锁、读写锁都属于**悲观锁**。悲观锁认为多线程同时修改共享资源的概率比较高，容易发生冲突，所以访问共享资源前先上锁。

如果多线程同时修改共享资源的概率比较低，可以采用**乐观锁**。乐观锁假定冲突概率很低，工作方式是：先修改共享资源，再验证这段时间内有没有发生冲突；如果没有其他线程修改资源，操作完成；如果发现资源已被其他线程修改，就放弃本次操作。

放弃后如何重试，与业务场景相关。虽然重试成本很高，但如果冲突概率足够低，仍然可以接受。乐观锁全程没有加锁，因此也称为无锁编程。

在线文档是一个典型场景。多个用户可以同时编辑同一份文档。如果使用悲观锁，只要一个用户正在编辑，其他用户就无法打开相同文档，体验很差。实际实现通常使用乐观锁：允许多个用户打开并编辑，提交时才验证是否冲突。

冲突验证通常依赖版本号：

- 浏览器下载文档时，记录服务端返回的文档版本号；
- 用户提交修改时，请求带上原始版本号；
- 服务端将请求中的版本号与当前版本号比较：不一致则提交失败，一致则修改成功，并更新版本号。

SVN 和 Git 也使用了乐观锁思想：先让用户编辑代码，提交时通过版本号判断是否冲突；发生冲突的地方需要手动修改后重新提交。

乐观锁去除了加锁解锁操作，但一旦发生冲突，重试成本非常高。因此，只有在冲突概率非常低、加锁成本非常高的场景，才考虑使用乐观锁。

> CAS 与自旋锁的定位

乐观锁先修改共享资源，再验证是否冲突；悲观锁在修改共享数据前先加锁，防止竞争。

CAS 本身是乐观锁，但自旋锁在 CAS 之外增加了 `while` 循环或睡眠 CPU 的操作，形成自旋效果：加锁失败会忙等待直到拿到锁。自旋锁需要事先拿到锁才能修改数据，因此仍属于悲观锁。

## 信号量与经典同步问题

信号量是操作系统提供的一种协调共享资源访问的方法，通常表示资源的数量，对应一个整型变量 `sem`。

信号量通过两种原子操作控制：

- **P 操作**：将 `sem` 减 1。相减后，如果 `sem < 0`，则进程或线程进入阻塞等待；否则继续执行。P 操作可能阻塞。
- **V 操作**：将 `sem` 加 1。相加后，如果 `sem <= 0`，则唤醒一个等待中的进程或线程。V 操作不会阻塞。

P 操作用于进入临界区之前，V 操作用于离开临界区之后，两者必须成对出现。

> V 操作中 `sem <= 0` 的判断

没有写反。假设 `sem = 1`，三个线程依次执行 P 操作：

- 第一个线程 P 操作后，`sem = 0`；
- 第二个线程 P 操作后，`sem = -1`；
- 第三个线程 P 操作后，`sem = -2`。

此时第一个线程执行 V 操作，`sem` 变为 `-1`。因为 `sem <= 0`，说明仍有线程阻塞，需要唤醒第二或第三个线程。

### 信号量实现互斥

为每类共享资源设置一个信号量 `s`，初值为 `1`，表示临界资源未被占用。把进入临界区的操作置于 `P(s)` 和 `V(s)` 之间，即可实现进程或线程互斥。

![互斥信号量](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/18-%E4%BA%92%E6%96%A5%E4%BF%A1%E5%8F%B7%E9%87%8F.jpg)

第一个线程执行 P 操作后，`s` 变为 0，表示临界资源空闲，可以分配给该线程。第二个线程执行 P 操作后，`s` 变为负值，表示临界资源已被占用，第二个线程被阻塞。直到第一个线程执行 V 操作，`s` 恢复为 0，唤醒第二个线程；第二个线程访问完毕再执行 V 操作，`s` 恢复到初始值 1。

对于两个并发线程，互斥信号量的值仅取 1、0 和 -1 三个值：

- `1`：没有线程进入临界区；
- `0`：有一个线程进入临界区；
- `-1`：一个线程进入临界区，另一个线程等待进入。

### 信号量实现同步

同步信号量的初值设为 `0`。以「吃饭-做饭」为例：

- 妈妈线程执行 `P(s1)`，相当于询问是否需要做饭。`s1` 初值为 0，执行后变为 -1，表示暂时不需要做饭，妈妈线程进入等待；
- 儿子肚子饿时执行 `V(s1)`，`s1` 从 -1 变为 0，唤醒妈妈线程，妈妈开始做饭；
- 儿子线程执行 `P(s2)`，询问饭是否做好。`s2` 初值为 0，执行后变为 -1，表示饭还没做好，儿子线程等待；
- 妈妈做完饭后执行 `V(s2)`，`s2` 从 -1 变为 0，唤醒儿子线程，儿子开始吃饭。

![信号量实现同步](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/19-%E4%BA%92%E6%96%A5%E4%BF%A1%E5%8F%B7%E9%87%8F%E5%90%8C%E6%AD%A5%E5%AE%9E%E7%8E%B0-%E5%90%83%E9%A5%AD%E4%BE%8B%E5%AD%90.jpg)

### 生产者-消费者问题

生产者-消费者问题的描述：

- **生产者**生成数据后，放在一个缓冲区中；
- **消费者**从缓冲区取出数据处理；
- 任何时刻，**只能有一个**生产者或消费者访问缓冲区。

问题分析：

- 任何时刻只能有一个线程操作缓冲区，说明操作缓冲区是临界代码，需要互斥；
- 缓冲区空时，消费者必须等待生产者生成数据；缓冲区满时，生产者必须等待消费者取出数据。生产者和消费者需要同步。

需要三个信号量：

- 互斥信号量 `mutex`：用于互斥访问缓冲区，初值为 1；
- 资源信号量 `fullBuffers`：消费者询问缓冲区是否有数据，初值为 0；
- 资源信号量 `emptyBuffers`：生产者询问缓冲区是否有空位，初值为 n（缓冲区大小）。

![生产者-消费者模型](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/20-%E7%94%9F%E4%BA%A7%E8%80%85%E6%B6%88%E8%B4%B9%E8%80%85.jpg)

```c
semaphore mutex = 1;
semaphore fullBuffers = 0;
semaphore emptyBuffers = n;

// 生产者
void producer() {
    P(emptyBuffers);   // 等待空位
    P(mutex);          // 进入临界区
    put(data);         // 放入数据
    V(mutex);          // 离开临界区
    V(fullBuffers);    // 通知消费者：有数据了
}

// 消费者
void consumer() {
    P(fullBuffers);    // 等待数据
    P(mutex);          // 进入临界区
    data = get();      // 取出数据
    V(mutex);          // 离开临界区
    V(emptyBuffers);   // 通知生产者：有空位了
}
```

如果消费者一开始执行 `P(fullBuffers)`，`fullBuffers` 初值为 0，执行后变为 -1，说明缓冲区没有数据，消费者等待。

生产者执行 `P(emptyBuffers)`，减少一个空槽。如果没有其他生产者线程在临界区，生产者把数据放入缓冲区，然后执行 `V(fullBuffers)`，`fullBuffers` 从 -1 变为 0，说明有消费者正在等待数据，于是唤醒消费者。

消费者被唤醒后，如果没有其他消费者在读数据，就可以进入临界区读取数据。离开临界区后，把空槽数量加 1。

### 哲学家就餐问题

问题描述：

- 5 个哲学家围绕一张圆桌吃面；
- 桌子上有 5 支叉子，每两个哲学家之间放一支；
- 哲学家先思考，饿了就想进餐；
- 每个哲学家需要两支叉子，也就是左右两边的叉子，才能进餐；
- 吃完后把两支叉子放回原处，继续思考。

目标：保证哲学家们的动作有序进行，不会有人永远拿不到叉子。

![哲学家就餐模型](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/23-%E5%93%B2%E5%AD%A6%E5%AE%B6%E8%BF%9B%E9%A4%90%E6%A8%A1%E5%9E%8B.jpg)

**方案一：直接拿左右叉子**

每个哲学家先 `P(fork[i])` 拿左边叉子，再 `P(fork[(i + 1) % 5])` 拿右边叉子。

如果 5 个哲学家同时拿起左边的叉子，桌面上就没有叉子可用，没有人能拿到右边的叉子，所有哲学家都阻塞在第二次 P 操作上，发生死锁。

![方案一的问题](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/25-%E5%93%B2%E5%AD%A6%E5%AE%B6%E8%BF%9B%E9%A4%90-%E6%96%B9%E6%A1%88%E4%B8%80%E9%97%AE%E9%A2%98.jpg)

**方案二：拿叉子前加互斥信号量**

在拿叉子前增加一个互斥信号量，保证同一时刻只有一个哲学家进入「准备拿叉子」的临界区。

这样可以避免死锁，但每次只能有一位哲学家进餐。桌面上有 5 把叉子，理论上可以允许两位哲学家同时进餐，因此方案二的效率不高。

![方案二的问题](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/27-%E5%93%B2%E5%AD%A6%E5%AE%B6%E8%BF%9B%E9%A4%90-%E6%96%B9%E6%A1%88%E4%BA%8C%E9%97%AE%E9%A2%98.jpg)

**方案三：奇偶编号采用不同拿取顺序**

偶数编号的哲学家先拿左边叉子，再拿右边叉子；奇数编号的哲学家先拿右边叉子，再拿左边叉子。

这样不会出现所有哲学家同时拿起同一边叉子的情况，既不会死锁，也允许两位哲学家同时进餐。

![方案三](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/29-%E5%93%B2%E5%AD%A6%E5%AE%B6%E8%BF%9B%E9%A4%90-%E6%96%B9%E6%A1%88%E4%B8%89-%E5%9B%BE%E8%A7%A3.jpg)

**方案四：状态数组 + 每哲学家一个信号量**

用一个数组 `state` 记录每位哲学家的状态：进餐、思考、饥饿（正在试图拿叉子）。一个哲学家只有在两个邻居都没有进餐时，才可以进入进餐状态。

邻居编号由宏定义：

- `LEFT`：`(i + 5 - 1) % 5`
- `RIGHT`：`(i + 1) % 5`

例如 `i` 为 2，则 `LEFT` 为 1，`RIGHT` 为 3。

每个哲学家对应一个信号量 `s[i]`。想进餐的哲学家先把自己的状态设为「饥饿」，然后检查左右邻居是否都不在进餐；如果满足条件，就进入进餐状态并 `V(s[i])`，否则在 `P(s[i])` 上阻塞。吃完后把自己的状态设为「思考」，并检查左右邻居是否因自己释放叉子而可以进餐。

方案四同样不会死锁，也可以两位哲学家同时进餐。

![方案四](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E4%BA%92%E6%96%A5%E4%B8%8E%E5%90%8C%E6%AD%A5/31-%E5%93%B2%E5%AD%A6%E5%AE%B6%E8%BF%9B%E9%A4%90-%E6%96%B9%E6%A1%88%E5%9B%9B-%E5%9B%BE%E8%A7%A3.jpg)

### 读者-写者问题

读者-写者问题为数据库访问建立了一个模型：读者只读取数据，不修改数据；写者既可以读，也可以修改数据。

约束条件：

- 「读-读」允许：同一时刻允许多个读者同时读；
- 「读-写」互斥：没有写者时读者才能读，没有读者时写者才能写；
- 「写-写」互斥：没有其他写者时，写者才能写。

**方案一：读者优先**

使用以下变量：

- 信号量 `wMutex`：控制写操作的互斥信号量，初值为 1；
- 读者计数 `rCount`：正在进行读操作的读者个数，初值为 0；
- 信号量 `rCountMutex`：控制对 `rCount` 的互斥修改，初值为 1。

读者进入时，先对 `rCount` 加 1；如果是第一个读者，则 `P(wMutex)`，阻止写者进入。读者离开时，对 `rCount` 减 1；如果是最后一个读者，则 `V(wMutex)`，允许写者进入。

```c
// 读者
P(rCountMutex);
if (rCount == 0) {
    P(wMutex);
}
rCount++;
V(rCountMutex);

read_data();

P(rCountMutex);
rCount--;
if (rCount == 0) {
    V(wMutex);
}
V(rCountMutex);
```

这种实现是读者优先：只要有读者正在读，后来的读者都可以直接进入。如果读者持续不断进入，写者会处于饥饿状态。

**方案二：写者优先**

在方案一的基础上增加：

- 信号量 `rMutex`：控制读者进入的互斥信号量，初值为 1；
- 信号量 `wDataMutex`：控制写者写操作的互斥信号量，初值为 1；
- 写者计数 `wCount`：记录写者数量，初值为 0；
- 信号量 `wCountMutex`：控制 `wCount` 的互斥修改，初值为 1。

写者到达时，先对 `wCount` 加 1；如果是第一个写者，则 `P(rMutex)`，阻止后续读者进入。写者离开时，对 `wCount` 减 1；如果是最后一个写者，则 `V(rMutex)`，允许读者进入。

这样，只要写者准备写入，后续读者就会被阻塞；如果写者持续不断，读者会处于饥饿状态。

**方案三：公平策略**

读者优先和写者优先都可能造成饥饿。公平策略的目标是：

- 读者和写者优先级相同；
- 写者、读者互斥访问；
- 只能有一个写者访问临界区；
- 可以有多个读者同时访问临界资源。

一种实现是增加信号量 `flag`。读者到达时先 `P(flag)`，进入读者队列后再 `V(flag)`；写者到达时也先 `P(flag)`。这样读者和写者都要先通过同一个入口排队，避免读者凭借「后续读者可直接进入」的特殊权限无限进入。写者拿到 `flag` 后，仍需等待当前读者全部退出，才能获得 `wDataMutex` 开始写。

## 死锁

在多线程编程中，为了防止多线程竞争共享资源导致数据错乱，通常会在操作共享资源之前加互斥锁。只有成功获取锁的线程才能操作共享资源；获取不到锁的线程只能等待，直到锁被释放。

当两个线程为了保护两个不同的共享资源而使用两个互斥锁，且使用不当时，可能造成**两个线程都在等待对方释放锁**。在没有外力作用下，这些线程会一直相互等待，无法继续运行，这种情况就是**死锁**。

例如，线程 A 持有资源 1，等待资源 2；线程 B 持有资源 2，等待资源 1。双方都在等待对方释放资源，形成循环等待。

### 死锁的四个必要条件

死锁只有**同时满足**以下四个条件才会发生：

- 互斥条件；
- 持有并等待条件；
- 不可剥夺条件；
- 环路等待条件。

**互斥条件**：多个线程不能同时使用同一个资源。线程 A 已经持有的资源，不能再同时被线程 B 持有；如果线程 B 请求获取线程 A 已占用的资源，只能等待。

![互斥条件](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%AD%BB%E9%94%81/%E4%BA%92%E6%96%A5%E6%9D%A1%E4%BB%B6.png)

**持有并等待条件**：线程 A 已经持有资源 1，又想申请资源 2，而资源 2 已被线程 C 持有。线程 A 在等待资源 2 的同时，不会释放自己已经持有的资源 1。

![持有并等待条件](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%AD%BB%E9%94%81/%E6%8C%81%E6%9C%89%E5%B9%B6%E7%AD%89%E5%BE%85%E6%9D%A1%E4%BB%B6.png)

**不可剥夺条件**：线程已经持有的资源，在自己使用完之前不能被其他线程获取。线程 B 如果也想使用此资源，只能在线程 A 使用完并释放后才能获取。

![不可剥夺条件](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%AD%BB%E9%94%81/%E4%B8%8D%E5%8F%AF%E5%89%A5%E5%A4%BA%E6%9D%A1%E4%BB%B6.png)

**环路等待条件**：死锁发生时，两个线程获取资源的顺序构成环形链。线程 A 已持有资源 2，想请求资源 1；线程 B 已获取资源 1，想请求资源 2，形成资源请求等待的环形图。

![环路等待条件](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E6%AD%BB%E9%94%81/%E7%8E%AF%E8%B7%AF%E7%AD%89%E5%BE%85%E6%9D%A1%E4%BB%B6.png)

### 死锁复现

创建两个线程 A、B，以及两个互斥锁 `mutex_A`、`mutex_B`：

```c
pthread_mutex_t mutex_A = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_t mutex_B = PTHREAD_MUTEX_INITIALIZER;

void *threadA(void *data) {
    pthread_mutex_lock(&mutex_A);
    sleep(1);
    pthread_mutex_lock(&mutex_B);
    pthread_mutex_unlock(&mutex_B);
    pthread_mutex_unlock(&mutex_A);
    return NULL;
}

void *threadB(void *data) {
    pthread_mutex_lock(&mutex_B);
    sleep(1);
    pthread_mutex_lock(&mutex_A);
    pthread_mutex_unlock(&mutex_A);
    pthread_mutex_unlock(&mutex_B);
    return NULL;
}
```

线程 A 先获取锁 A，睡眠 1 秒，再获取锁 B；线程 B 先获取锁 B，睡眠 1 秒，再获取锁 A。运行后，线程 A 等待锁 B，线程 B 等待锁 A，双方互相等待，形成死锁。

### 死锁排查

Java 程序可以使用 `jstack` 排查死锁。`jstack` 是 JDK 自带的线程堆栈分析工具。

`p mutex_A` 显示锁 A 被 LWP 87747（线程 A）持有；`p mutex_B` 显示锁 B 被 LWP 87748（线程 B）持有。线程 B 在等待线程 A 持有的锁 A，线程 A 在等待线程 B 持有的锁 B，因此可以断定程序发生了死锁。

### 避免死锁

产生死锁的四个必要条件是互斥、持有并等待、不可剥夺、环路等待。避免死锁只需要破坏其中一个条件即可。最常见且可行的方式是**资源有序分配法**，用来破坏环路等待条件。

资源有序分配法的要求是：所有线程以相同的顺序申请资源。线程 A 先申请资源 A，再申请资源 B；线程 B 也先申请资源 A，再申请资源 B。这样不会形成环形等待。

修改前面的例子时，线程 A 的代码可以保持不变；线程 B 改为先获取 `mutex_A`，再获取 `mutex_B`：

```c
void *threadB(void *data) {
    pthread_mutex_lock(&mutex_A);
    sleep(1);
    pthread_mutex_lock(&mutex_B);
    pthread_mutex_unlock(&mutex_B);
    pthread_mutex_unlock(&mutex_A);
    return NULL;
}
```

这样两个线程的加锁顺序一致，不会发生死锁。

## 进程间通信

每个进程的用户地址空间都是独立的，一般情况下无法相互访问；但内核空间是所有进程共享的。因此，进程之间要通信，必须经过内核。

![进程地址空间与共享的内核空间](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1/4-%E8%BF%9B%E7%A8%8B%E7%A9%BA%E9%97%B4.jpg)

Linux 内核提供了多种进程间通信（IPC）机制，包括管道、消息队列、共享内存、信号量、信号以及跨主机的 Socket。

![进程间通信机制提纲](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1/3-%E6%8F%90%E7%BA%B2.jpg)

### 管道

shell 中的 `|` 就是管道：

```bash
$ ps auxf | grep mysql
```

它把前一个命令（`ps auxf`）的输出作为后一个命令（`grep mysql`）的输入，因此**管道是单向的**；需要双向通信时，要创建两个管道。这种管道没有名字、用完即销毁，称为**匿名管道**。

另一类是**命名管道**，也就是 `FIFO`，数据先进先出。使用前用 `mkfifo` 创建并指定名字：

```bash
$ mkfifo myPipe
```

`myPipe` 即管道名。基于「一切皆文件」的设计，管道也以文件形式存在，用 `ls -l` 可以看到它的类型是 `p`（pipe）：

```bash
$ ls -l
prw-r--r--. 1 root    root         0 Jul 17 02:45 myPipe
```

往管道写数据：

```bash
$ echo "hello" > myPipe   # 把数据写进管道
                          # 命令停在这里
```

命令会阻塞在这里：管道里的内容还没有被读取，只有数据被读走，写端的命令才会退出。另起一个命令读取：

```bash
$ cat < myPipe   # 读取管道里的数据
hello
```

数据被读出并打印到终端，`echo` 那条命令也随之正常退出。

由此可见，**管道效率低，不适合进程间频繁交换数据**；好处是简单，而且能确知数据已被对方读走。

> 管道的创建与原理

匿名管道通过下面的系统调用创建：

```c
int pipe(int fd[2])
```

它创建一个匿名管道并返回两个描述符：`fd[0]` 是读端，`fd[1]` 是写端。匿名管道是只存在于内存的特殊文件，不在文件系统中。

![pipe 系统调用](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1/5-%E7%AE%A1%E9%81%93-pipe.jpg)

**所谓管道，本质是内核里的一串缓存**：写入端的数据缓存在内核，读取端也从内核取走。管道传输的是无格式字节流，且大小受限。

但两个描述符还在同一个进程里，并不能跨进程。办法是用 `fork` 创建子进程，**子进程会复制父进程的文件描述符**，于是两个进程各持一套 `fd[0]`/`fd[1]`，读写同一个管道即可完成跨进程通信。

![fork 之后共享管道](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1/6-%E7%AE%A1%E9%81%93-pipe-fork.jpg)

管道只能一端写、另一端读，父子双方都能读写容易混乱，通常的做法是：

- 父进程关闭读端 `fd[0]`，只保留写端 `fd[1]`；
- 子进程关闭写端 `fd[1]`，只保留读端 `fd[0]`。

![单向通信](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1/7-%E7%AE%A1%E9%81%93-pipe-fork-%E5%8D%95%E5%90%91%E9%80%9A%E4%BF%A1.jpg)

需要双向通信，就创建两个管道。

不过 shell 里的情况并非如此。执行 `A | B` 时，A 与 B 都是由 shell 创建的子进程，两者之间不存在父子关系，它们的父进程都是 shell。

![shell 中的管道](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1/8-%E7%AE%A1%E9%81%93-pipe-shell.jpg)

所以 shell 用 `|` 连接多个命令，实际是创建了多个子进程；写脚本时能用一条管道解决的事就不必多建一条，以减少创建子进程的系统开销。

由此可得：**匿名管道的通信范围局限于有父子关系的进程**——管道没有实体文件，只能靠 `fork` 复制父进程的 fd 来共享。

而**命名管道可以在互不相关的进程之间通信**：它预先在文件系统里创建了一个类型为管道的设备文件，进程打开该文件即可通信。

无论匿名还是命名管道，写入的数据都缓存在内核，读取也从内核取，且遵循**先进先出**，不支持 `lseek` 这类文件定位操作。

### 消息队列

管道效率低，不适合频繁交换数据，**消息队列**可以解决这个问题：A 进程把数据放进消息队列后即可返回，B 进程需要时再去取；反向亦然。

**消息队列是保存在内核中的消息链表**。发送时数据被分成一个个独立的数据单元，即消息体；消息体是用户自定义的数据类型，收发双方必须约定好类型，因此每个消息体都是固定大小的存储块，不像管道是无格式字节流。进程从队列中取走消息体后，内核会删除它。

消息队列的生命周期随内核：只要不释放队列、不重启系统，它就一直存在；而匿名管道随进程创建而建立、随进程结束而销毁。

这种模型类似收发邮件，双方可以频繁往来；但邮件也有两个不足——**通信不及时**、**附件大小受限**，消息队列同样如此。

**消息队列不适合传输大数据**：内核中每个消息体都有最大长度限制，队列内所有消息体的总长度也有上限。Linux 内核用两个宏 `MSGMAX` 和 `MSGMNB`（以字节为单位）分别限定单条消息的最大长度和一个队列的最大长度。

**消息队列还存在用户态与内核态之间的拷贝开销**：进程写入时要把数据从用户态拷到内核态，另一进程读取时又要从内核态拷回用户态。

### 共享内存

消息队列的读写都要在用户态与内核态之间拷贝，**共享内存**正是为了消除这份开销。

现代操作系统采用虚拟内存技术：每个进程有独立的虚拟地址空间，不同进程的虚拟内存映射到不同的物理内存。因此即使进程 A 与进程 B 的虚拟地址相同，访问的也是不同的物理内存，数据的增删改互不影响。

**共享内存的做法，是把一块虚拟地址空间映射到同一块物理内存上**。这样一个进程写入的内容，另一个进程立刻可见，中间不需要任何拷贝，通信速度大幅提升。

![共享内存](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1/9-%E5%85%B1%E4%BA%AB%E5%86%85%E5%AD%98.jpg)

共享内存是最快的进程间通信方式，但多个进程同时修改同一块共享内存会产生竞争，因此需要配合信号量等机制实现互斥与同步。

### 信号量

信号量是一个整型计数器，用于进程间的互斥与同步，本身不用于缓存通信数据。

P 操作把信号量减 1：减后若小于 0，说明资源已被占用，进程阻塞等待；若大于等于 0，说明还有资源可用，继续执行。

V 操作把信号量加 1：加后若小于等于 0，说明当前有进程阻塞，需要唤醒；若大于 0，说明当前没有阻塞的进程。

- 信号量初值为 `1` 时，可以作为**互斥信号量**，保证共享资源在任意时刻只有一个进程访问；
- 信号量初值为 `0` 时，可以作为**同步信号量**，保证进程 A 在进程 B 之前执行。

信号量的 P/V 操作、互斥与同步的具体用法，前面「信号量与经典同步问题」已经详细讨论，这里不再重复。作为 IPC 机制，信号量通常与共享内存配合使用：共享内存负责传输数据，信号量负责保护数据。

信号与信号量名字相近，用途却完全不同，关系有些类似 Java 与 JavaScript。

- `Ctrl+Z` 产生 `SIGTSTP`，停止该进程但并未结束。

- `kill -9 1050`：向 PID 为 1050 的进程发送 `SIGKILL`，立即结束它。

所以信号事件的来源主要有硬件（如键盘 `Ctrl+C`）和软件（如 `kill` 命令）两类。

信号是**异步通信机制**：任何时候都可以把信号发给某个进程。信号产生后，用户进程有三种处理方式：

1. **执行默认操作**：Linux 为每种信号规定了默认动作，例如 `SIGTERM` 就是终止进程；
2. **捕捉信号**：为信号定义处理函数，信号发生时执行该函数；
3. **忽略信号**：不处理某些信号。但 `SIGKILL` 与 `SIGSTOP` 无法被捕捉或忽略，它们用于在任何时候中断或结束进程。

### Socket

以上机制都局限于同一台主机。**跨网络与不同主机上的进程通信，要用 Socket**；Socket 同样可以用于同主机内的进程间通信。

创建 socket 的系统调用：

```c
int socket(int domain, int type, int protocol)
```

三个参数的含义：

- `domain`：协议族，如 `AF_INET`（IPv4）、`AF_INET6`（IPv6）、`AF_LOCAL`/`AF_UNIX`（本机）；
- `type`：通信特性，如 `SOCK_STREAM`（字节流，对应 TCP）、`SOCK_DGRAM`（数据报，对应 UDP）、`SOCK_RAW`（原始套接字）；
- `protocol`：原本用于指定协议，现已基本废弃——协议由前两个参数确定，一般写 0。

按 socket 类型不同，通信方式也不同：

- TCP 字节流：`AF_INET` + `SOCK_STREAM`；
- UDP 数据报：`AF_INET` + `SOCK_DGRAM`；
- 本地进程间通信：`AF_LOCAL` + `SOCK_STREAM`（本地字节流）或 `AF_LOCAL` + `SOCK_DGRAM`（本地数据报）。`AF_UNIX` 与 `AF_LOCAL` 等价，也属于本地 socket。

> TCP 的 socket 编程模型

![TCP 编程模型](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1/12-TCP%E7%BC%96%E7%A8%8B%E6%A8%A1%E5%9E%8B.jpg)

- 服务端与客户端各自初始化 `socket`，得到文件描述符；
- 服务端调用 `bind`，绑定 IP 地址与端口；
- 服务端调用 `listen`，开始监听；
- 服务端调用 `accept`，等待客户端连接；
- 客户端调用 `connect`，向服务端地址与端口发起连接；
- 服务端 `accept` 返回用于传输的 socket 描述符；
- 客户端 `write` 写入数据，服务端 `read` 读取数据；
- 客户端断开时调用 `close`，服务端 `read` 会读到 EOF，处理完数据后再 `close`，连接关闭。

注意服务端 `accept` 成功时返回的是一个**已完成连接的 socket**，之后用它传输数据。所以在 TCP 里存在**两个 socket**：监听 socket 与已完成连接 socket。

连接建立后，双方通过 `read`/`write` 读写数据，如同往文件流里写东西。

> UDP 的 socket 编程模型

![UDP 编程模型](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E6%93%8D%E4%BD%9C%E7%B3%BB%E7%BB%9F/%E8%BF%9B%E7%A8%8B%E9%97%B4%E9%80%9A%E4%BF%A1/13-UDP%E7%BC%96%E7%A8%8B%E6%A8%A1%E5%9E%8B.jpg)

UDP 无连接，不需要三次握手，也就不需要 `listen` 和 `connect`；但交互仍需 IP 地址与端口，因此同样要 `bind`。

UDP 不维护连接，没有明确的发送方与接收方，甚至不存在客户端与服务端的概念，一个 socket 就能与多台机器任意通信，因此每个 UDP socket 都需要 `bind`；并且每次 `sendto`/`recvfrom` 都要传入目标主机的 IP 地址与端口。

> 本地进程间通信的 socket 编程模型

本地 socket 用于**同一台主机内的进程间通信**：

- 编程接口与 IPv4/IPv6 套接字一致，同样支持「字节流」与「数据报」两种协议；
- 实现效率明显高于 IPv4/IPv6 的字节流、数据报 socket。

本地字节流 socket 使用 `AF_LOCAL` + `SOCK_STREAM`，本地数据报 socket 使用 `AF_LOCAL` + `SOCK_DGRAM`。

与 TCP/UDP 最大的区别在 `bind` 的对象：本地 socket 绑定的是**一个本地文件**，而非 IP 地址与端口。

### TD

| 机制             | 关键特点                                                                       | 主要限制                                               |
| ---------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 匿名管道         | 单向无格式字节流；`pipe()` 创建，`fork` 复制 fd 共享；数据缓存在内核、先进先出 | 只能用于有父子关系的进程；效率低                       |
| 命名管道（FIFO） | 以文件系统中类型为 `p` 的设备文件存在                                          | 同样不支持 `lseek` 等定位操作；效率低                  |
| 消息队列         | 内核中的消息链表，消息体定长、类型由用户定义                                   | 受 `MSGMAX`/`MSGMNB` 限制；读写各一次用户态/内核态拷贝 |
| 共享内存         | 同一块物理内存映射到多个进程的地址空间，全程无拷贝                             | 需配合信号量等机制解决竞争                             |
| 信号量           | 整型计数器，P/V 原子操作；初值 1 实现互斥、初值 0 实现同步                     | 本身不传递数据                                         |
| 信号             | 异步通知；来源分硬件与软件；可默认处理、捕捉或忽略                             | `SIGKILL`、`SIGSTOP` 不可捕捉或忽略                    |
| Socket           | 可跨主机，也可本机；按 `domain`/`type` 分为 TCP、UDP、本地 socket              | 编程复杂，需协议栈参与                                 |

同一进程内的线程共享地址空间，用共享变量（如全局变量）即可完成线程间通信；因此线程之间更值得关心的是**竞争**问题，同样可以用信号量的互斥与同步来解决：

- 互斥：保证任意时刻只有一个线程访问共享资源；
- 同步：保证线程 A 在线程 B 之前执行。

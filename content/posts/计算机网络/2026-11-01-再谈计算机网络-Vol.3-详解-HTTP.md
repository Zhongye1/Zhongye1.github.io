## 概述

HTTP 是应用层使用最广泛的协议之一。它的基本模型是「请求 - 响应」：客户端发送请求报文，服务端返回响应报文，报文由 Header 和 Body 构成。

随着页面资源变多、消息变大、实时性要求提高，HTTP/1.1 的性能瓶颈逐渐明显：并发连接有限、队头阻塞、头部重复且巨大、服务端不能主动推送。围绕这些问题，出现了一系列优化手段，并最终推动了 HTTP/2 和 HTTP/3 的设计。

本文按以下顺序展开：

- HTTP 基础：定义、状态码、常见字段、GET 与 POST、HTTP/1.1 的特性与性能；
- HTTP 缓存与 HTTP/1.1 优化：强制缓存、协商缓存、减少请求次数、压缩响应；
- HTTPS：安全风险、混合加密、证书、RSA 与 ECDHE 握手、HTTPS 优化与会话复用；
- HTTP/2：头部压缩、二进制帧、Stream 并发、服务器推送，以及 TCP 层队头阻塞；
- HTTP/3：QUIC 如何解决 TCP 队头阻塞、握手延迟和连接迁移问题。

## HTTP 基础

### HTTP 的定义

HTTP 是超文本传输协议（HyperText Transfer Protocol），可以拆成三个部分理解：

- **超文本**：传输内容不只是纯文本，还包括图片、视频、音频等，并且可以通过超链接从一个文档跳转到另一个文档；
- **传输**：数据在两个端点之间传递，中间可以经过代理、网关等中转节点；
- **协议**：参与者必须遵守的约定和规范，包括报文格式、请求方法、状态码、错误处理等。

因此，HTTP 可以定义为：**在计算机世界里，专门在两点之间传输文字、图片、音频、视频等超文本数据的约定和规范。**

HTTP 是双向协议。浏览器作为请求方发送请求，服务器作为应答方返回响应；通信双方也可以都是服务器。中间节点只要遵守 HTTP 协议，就可以在数据传输过程中添加缓存、代理、网关等功能。

![HTTP 的三个组成部分](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C/HTTP/3-HTTP%E4%B8%89%E9%83%A8%E5%88%86.png)

### 常见状态码

HTTP 状态码分为五类：

| 类别  | 含义       | 常见状态码                                                                                       |
| ----- | ---------- | ------------------------------------------------------------------------------------------------ |
| `1xx` | 提示信息   | 协议处理中的中间状态，实际使用较少                                                               |
| `2xx` | 成功       | `200 OK`、`204 No Content`、`206 Partial Content`                                                |
| `3xx` | 重定向     | `301 Moved Permanently`、`302 Found`、`304 Not Modified`                                         |
| `4xx` | 客户端错误 | `400 Bad Request`、`403 Forbidden`、`404 Not Found`                                              |
| `5xx` | 服务端错误 | `500 Internal Server Error`、`501 Not Implemented`、`502 Bad Gateway`、`503 Service Unavailable` |

几个容易混淆的状态码：

- `204 No Content`：成功，但响应没有 Body；
- `206 Partial Content`：返回部分资源，用于分块下载或断点续传；
- `301`：永久重定向，资源已迁移到新 URL；
- `302`：临时重定向，资源暂时用另一个 URL 访问；
- `304`：资源未修改，客户端可以继续使用缓存；
- `502`：网关或代理本身正常，但访问后端服务失败；
- `503`：服务端当前繁忙，暂时无法响应。

![五大类 HTTP 状态码](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C/HTTP/6-%E4%BA%94%E5%A4%A7%E7%B1%BBHTTP%E7%8A%B6%E6%80%81%E7%A0%81.png)

### 常见字段

**Host**：客户端发送请求时指定服务器的域名。有了 `Host`，同一台服务器可以承载多个网站。

```http
Host: www.example.com
```

**Content-Length**：服务器返回数据时，表明本次响应的数据长度。HTTP 通过回车换行作为 Header 的边界，通过 `Content-Length` 作为 Body 的边界，二者共同解决 TCP 字节流带来的粘包问题。

```http
Content-Length: 1000
```

**Connection**：用于控制连接管理。HTTP/1.1 默认使用长连接，但为了兼容老版本，常指定：

```http
Connection: Keep-Alive
```

长连接的特点是：只要任意一端没有明确提出断开连接，连接就保持。需要注意，HTTP 的 `Keep-Alive` 与 TCP 的 `Keepalive` 不是同一个机制。

**Content-Type**：服务器告诉客户端本次数据的格式。

```http
Content-Type: text/html; Charset=utf-8
```

客户端请求时可以用 `Accept` 声明自己可以接受的格式：

```http
Accept: */*
```

**Content-Encoding**：说明响应数据的压缩方式。

```http
Content-Encoding: gzip
```

客户端通过 `Accept-Encoding` 声明自己支持的压缩算法：

```http
Accept-Encoding: gzip, deflate, br
```

### GET 与 POST

从 RFC 语义看：

- **GET**：从服务器获取指定资源。参数通常放在 URL 中，URL 只支持 ASCII，浏览器还会对 URL 长度做限制（HTTP 协议本身没有规定 URL 长度上限）。GET 是安全、幂等、可缓存的。
- **POST**：根据请求 Body 对指定资源进行处理。数据放在 Body 中，可以是任意格式，浏览器不会限制 Body 大小。POST 通常不安全、不幂等、默认不缓存。

| 维度     | GET          | POST               |
| -------- | ------------ | ------------------ |
| 语义     | 获取资源     | 处理资源           |
| 参数位置 | 通常在 URL   | 通常在 Body        |
| 安全性   | 安全         | 不安全             |
| 幂等性   | 幂等         | 通常不幂等         |
| 缓存     | 可缓存       | 通常不缓存         |
| 书签     | 可保存为书签 | 通常不可保存为书签 |

实际开发中，方法语义不一定严格遵循 RFC。例如可以用 GET 实现删除操作，此时 GET 就不再安全；也可以用 POST 实现查询，此时 POST 也可以做到安全和幂等。

GET 请求理论上可以携带 Body，RFC 没有禁止；只是 GET 的语义是获取资源，通常不需要 Body。URL 查询参数也不是 GET 独有的，POST 的 URL 同样可以带参数。

### HTTP/1.1 的优点

- **简单**：报文格式是 `header + body`，头部是 `key-value` 文本，易于理解和实现；
- **灵活和易于扩展**：请求方法、URI、状态码、头字段都没有被完全固定，允许扩展；下层传输也可以变化，例如 HTTPS 在 HTTP 与 TCP 之间增加 TLS，HTTP/3 改用 UDP；
- **应用广泛、跨平台**：从浏览器到移动 App，从新闻、购物到音视频，HTTP 都有广泛应用。

### HTTP/1.1 的缺点

HTTP/1.1 有三类主要问题：

- **无状态**：服务器不记忆请求之间的状态。好处是减轻服务器负担；坏处是有关联的操作需要反复验证身份。常用 Cookie 解决：服务器在首次请求后下发 Cookie，后续请求携带 Cookie，服务器据此识别客户端。
- **明文传输**：报文内容在链路上可见，调试方便，但容易被窃听。敏感数据需要 HTTPS。
- **不安全**：不验证通信方身份，也无法证明报文完整性，可能遭遇窃听、篡改和冒充。

### HTTP/1.1 的性能

HTTP/1.1 基于 TCP/IP，并采用「请求 - 应答」模型，性能瓶颈主要来自以下方面：

- **长连接**：HTTP/1.0 每个请求都要新建 TCP 连接；HTTP/1.1 引入持久连接，减少 TCP 建立和断开的开销；
- **管道网络传输**：HTTP/1.1 允许在同一个 TCP 连接中连续发送多个请求，不必等前一个响应回来。但服务器必须按接收请求的顺序返回响应，如果前一个请求处理慢，后续响应会被阻塞。
- **队头阻塞**：管道解决了请求侧的队头阻塞，但没有解决响应侧的队头阻塞。实际使用中，HTTP/1.1 管道化默认不开启，浏览器基本不支持，因此讨论 HTTP/1.1 队头阻塞时通常不考虑管道模式。

浏览器通常对同一域名建立 5-6 个并发 TCP 连接，每个连接都要经历 TCP 握手、TLS 握手和 TCP 慢启动。页面资源越多，这部分开销越明显。

## HTTP 缓存与 HTTP/1.1 优化

HTTP/1.1 的优化思路可以归纳为三类：

- 尽量避免发送 HTTP 请求；
- 需要发送请求时，减少请求次数；
- 减少服务器响应的数据大小。

### 强制缓存

强制缓存：只要浏览器判断缓存没有过期，就直接使用本地缓存，是否使用缓存的主动权在浏览器。

强制缓存依赖两个响应头：

- `Cache-Control`：相对时间，例如 `max-age=3600`；
- `Expires`：绝对时间。

两者同时存在时，`Cache-Control` 优先级高于 `Expires`。`Cache-Control` 选项更多、设置更精细，通常优先使用。

工作流程：

1. 浏览器第一次请求资源，服务器在响应头中加上 `Cache-Control`，设置过期时间；
2. 浏览器再次请求该资源时，根据请求时间与 `Cache-Control` 的过期时间计算缓存是否过期；
3. 未过期则直接使用本地缓存；过期则重新请求服务器；
4. 服务器返回新响应时，再次更新 `Cache-Control`。

### 协商缓存

协商缓存：浏览器与服务器协商后，由服务器告知客户端是否可以使用本地缓存。常见响应状态码是 `304 Not Modified`。

协商缓存有两种实现方式。

**方式一：`Last-Modified` 与 `If-Modified-Since`**

- 响应头 `Last-Modified`：资源最后修改时间；
- 请求头 `If-Modified-Since`：缓存过期后，浏览器把上次的 `Last-Modified` 值带在请求中；
- 服务器比较资源当前最后修改时间与请求中的时间：资源有更新则返回 `200` 和新资源；没有更新则返回 `304`，客户端继续使用缓存。

**方式二：`ETag` 与 `If-None-Match`**

- 响应头 `ETag`：资源的唯一标识；
- 请求头 `If-None-Match`：缓存过期后，浏览器把上次的 `ETag` 值带在请求中；
- 服务器比较当前资源标识与请求中的标识：相同则返回 `304`；不同则返回 `200` 和新资源。

`ETag` 比 `Last-Modified` 更精确，原因包括：

- 文件内容没有变化时，修改时间也可能变化；
- `Last-Modified` 只能精确到秒，秒内多次修改无法识别；
- 有些服务器无法准确获取文件的最后修改时间。

如果响应同时带有 `ETag` 和 `Last-Modified`，客户端再次请求时通常两者都带上，服务器优先判断 `ETag`。

![协商缓存流程](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E7%BD%91%E7%BB%9C/http1.1%E4%BC%98%E5%8C%96/%E7%BC%93%E5%AD%98etag.png)

强制缓存与协商缓存通常配合使用：先判断强制缓存是否命中；未命中时，再发起带协商缓存字段的请求。

### 减少请求次数

**减少重定向请求**

资源迁移后，服务器可以通过 `302` 和 `Location` 告诉客户端新地址。重定向越多，客户端发起的请求越多，网络延迟越大。

如果重定向由代理服务器完成，客户端与代理之间可以减少一次消息传递；代理了解重定向规则后，还可以进一步减少消息往返。

`301` 和 `308` 表示永久重定向，客户端可以缓存重定向结果，后续直接用新 URL 访问。

**合并请求**

把多个小文件请求合并成一个大请求，虽然总资源不变，但减少了重复的 HTTP 头部，也减少了 TCP 连接数量，从而省去 TCP 握手和慢启动的开销。

常见方式：

- **CSS Image Sprites**：把多张小图合成一张大图，浏览器一次请求获取大图，再用 CSS 切割使用；
- **打包工具**：用 Webpack 等把多个 JS、CSS 文件打包成一个大文件；
- **Base64 内嵌**：把图片二进制数据用 Base64 编码后嵌入 HTML 或 CSS，减少图片请求。

合并请求的代价是：大资源中某个小资源变化时，客户端必须重新下载整个大资源。

**延迟发送请求**

按需获取资源：页面初次加载时只获取当前可见区域需要的资源，用户滚动页面时再请求后续资源。这样减少首屏请求数量，但可能增加后续交互的请求次数。

### 减少响应数据大小

响应资源通常比请求大，压缩是主要优化方向。压缩分为无损压缩和有损压缩。

**无损压缩**

压缩后可以完全恢复原始数据，适合文本、代码、可执行文件。常见做法是去除代码中的换行和空格，再用 Huffman 编码等算法压缩。

gzip 是常见的无损压缩。客户端通过 `Accept-Encoding` 告诉服务器支持的算法，服务器选择一种压缩响应资源，并通过 `Content-Encoding` 告诉客户端使用的算法。

Brotli（`br`）的压缩效率通常高于 gzip，服务器支持时可以优先选择 Brotli。

**有损压缩**

有损压缩会舍弃次要数据，解压后的数据与原始数据不完全相同，但非常接近。常用于图片、音频、视频。

- 图片：WebP 通常比 PNG 压缩比更高，适合大量图片的网站；
- 视频：利用连续帧之间的相似性，只编码变化部分，常见编码有 H.264、H.265；
- 音频：常见编码有 AAC、AC3。

### 优化手段的边界

HTTP/1.1 的优化手段大多是在协议外部做文章：合并资源、内嵌资源、分域名、压缩内容。这些手段能缓解问题，但无法改变 HTTP/1.1 的关键限制：

- 请求 - 响应模型；
- 头部巨大且重复；
- 并发连接需要多次握手；
- 服务器不能主动推送。

要改变这些限制，必须重新设计 HTTP 的传输方式，这就是 HTTP/2 和 HTTP/3 的出发点。

## HTTPS

### HTTP 的安全风险

HTTP 是明文传输，存在三类风险：

- **窃听风险**：通信链路上的内容可以被截获；
- **篡改风险**：中间人可以修改通信内容，例如植入广告；
- **冒充风险**：中间人可以冒充服务器，例如伪造银行或购物网站。

HTTPS 在 HTTP 与 TCP 之间加入 TLS 协议，解决上述问题：

- **信息加密**：交互信息被加密，第三方无法直接读取；
- **校验机制**：校验信息是否被篡改，篡改后无法正常通过验证；
- **身份证书**：证明服务器身份，防止冒充。

![HTTPS 与 HTTP 的网络层](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C/HTTP/19-HTTPS%E4%B8%8EHTTP.png)

HTTP 与 HTTPS 的主要区别：

- HTTP 明文传输；HTTPS 在 TCP 与 HTTP 之间增加 TLS，报文加密传输；
- HTTP 只需 TCP 三次握手；HTTPS 还需要 TLS 握手；
- HTTP 默认端口 80；HTTPS 默认端口 443；
- HTTPS 需要向 CA 申请数字证书，证明服务器身份。

### 混合加密

HTTPS 采用对称加密与非对称加密结合的混合加密：

- 通信建立前，用非对称加密交换会话密钥；
- 通信过程中，用对称加密的会话密钥加密明文数据。

原因在于两种加密方式各有取舍：

- **对称加密**：只使用一个密钥，运算速度快，但密钥必须保密，无法安全地完成密钥交换；
- **非对称加密**：使用公钥和私钥，公钥可以公开分发，私钥保密，可以解决密钥交换问题，但运算速度慢。

### 摘要、数字签名与数字证书

**摘要算法**用于保证完整性：对内容计算哈希值，得到内容的「指纹」。接收方对内容重新计算哈希值，与发送方的指纹比较；相同则内容未被篡改。

摘要算法只能保证内容完整性，不能证明消息来源。中间人可以同时替换内容和哈希值，因此需要数字签名。

**数字签名**使用非对称加密：

- 公钥加密、私钥解密：保证内容传输的机密性；
- 私钥加密、公钥解密：证明消息来自持有私钥的一方。

数字签名通常不是对内容本身加密，而是对内容的哈希值加密。服务端用私钥对哈希值签名，客户端用服务端公钥验证签名。

**数字证书**解决公钥身份问题。证书通常包含：

- 公钥；
- 持有者信息；
- CA 信息；
- CA 对证书的数字签名及算法；
- 证书有效期；
- 其他扩展信息。

CA 签发证书的过程：

1. 把持有者公钥、用途、颁发者、有效期等信息打包；
2. 对信息做 Hash 计算；
3. 用 CA 私钥加密 Hash 值，生成证书签名；
4. 把签名附加到证书上，形成数字证书。

客户端验证证书的过程：

1. 用同样的 Hash 算法计算证书的 Hash 值 H1；
2. 用本地预置的 CA 公钥解密证书签名，得到 H2；
3. 比较 H1 与 H2，相同则证书可信。

![证书签发与验证](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E7%BD%91%E7%BB%9C/https/%E8%AF%81%E4%B9%A6%E7%9A%84%E6%A0%A1%E9%AA%8C.png)

实际证书通常不是由根证书直接签发，而是由中间证书签发，形成证书链：

- 客户端信任根证书；
- 根证书签发中间证书；
- 中间证书签发服务器证书。

客户端从服务器证书出发，逐级向上验证签名，直到找到本地信任的根证书。根证书数量很少，操作系统和浏览器会预置根证书列表。

![证书信任链](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E7%BD%91%E7%BB%9C/https/%E8%AF%81%E4%B9%A6%E9%93%BE.png)

### TLS 握手：RSA

RSA 是传统的密钥交换算法。客户端生成随机密钥，用服务端公钥加密后传给服务端；服务端用私钥解密，双方得到相同的会话密钥。

TLS 1.2 的 RSA 握手通常包含四次握手，约 2 个 RTT：

![TLS 四次握手](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E7%BD%91%E7%BB%9C/https/tls%E6%8F%A1%E6%89%8B.png)

**第一次握手：Client Hello**

客户端发送：

- 支持的 TLS 版本；
- 支持的密码套件列表；
- 客户端随机数 `Client Random`。

**第二次握手：Server Hello**

服务端返回：

- 确认的 TLS 版本；
- 服务端随机数 `Server Random`；
- 选定的密码套件；
- 服务器证书；
- `Server Hello Done`，表示服务端信息发送完毕。

密码套件的基本格式是：

```text
密钥交换算法 + 签名算法 + 对称加密算法 + 摘要算法
```

例如 `TLS_RSA_WITH_AES_128_GCM_SHA256` 表示：

- 密钥交换和签名都使用 RSA；
- 对称加密使用 AES-128-GCM；
- 摘要算法使用 SHA256。

**第三次握手：客户端回应**

客户端验证证书后，从证书中取出服务端公钥，生成 `pre-master` 随机数，并用服务端公钥加密，通过 `Client Key Exchange` 发送给服务端。

随后客户端发送：

- `Change Cipher Spec`：通知后续使用会话密钥加密；
- `Encrypted Handshake Message`：把之前握手数据的摘要用会话密钥加密，供服务端验证。

**第四次握手：服务端回应**

服务端用私钥解密得到 `pre-master`，结合 `Client Random`、`Server Random` 生成会话密钥，然后发送：

- `Change Cipher Spec`；
- `Encrypted Handshake Message`。

双方验证加密和解密正常后，握手完成，开始用会话密钥传输 HTTP 数据。

RSA 握手的最大问题是不支持前向保密：客户端用服务端公钥加密 `pre-master`，一旦服务端私钥泄漏，过去截获的所有密文都可能被破解。

### TLS 握手：ECDHE

ECDHE 基于椭圆曲线 Diffie-Hellman 算法，支持前向保密，是目前广泛使用的密钥交换算法。

#### 离散对数与 DH

DH 算法基于离散对数问题。双方公开参数：

- 模数 `P`；
- 底数 `G`。

双方各自生成私钥 `a`、`b`，并计算公钥：

```text
A = G^a mod P
B = G^b mod P
```

双方交换公钥后，各自计算共享密钥：

```text
K = B^a mod P = A^b mod P
```

公开信息包括 `P`、`G`、`A`、`B`；私钥 `a`、`b` 不公开。当 `P` 是很大的质数时，从公钥反推私钥在计算上不可行，这就是 DH 的安全基础。

#### DHE 与 ECDHE

static DH 中有一方私钥固定，长期使用后可能被暴力破解，不具备前向安全性。

DHE 中双方的私钥都是临时随机生成的，每次通信的私钥彼此独立。即使某一次私钥被破解，其他通信的私钥仍然安全，这就是前向安全。

DHE 需要大量乘法运算，性能不佳。ECDHE 在 DHE 基础上利用椭圆曲线特性，用更少的计算量完成密钥协商。

ECDHE 的过程：

- 双方约定椭圆曲线和基点 `G`；
- 双方各自生成私钥 `d`，计算公钥 `Q = dG`；
- 交换公钥后，双方计算共享点：

```text
d1Q2 = d1d2G = d2d1G = d2Q1
```

共享点的 x 坐标相同，作为共享密钥。实际 TLS 中，最终会话密钥由三部分生成：

```text
Client Random + Server Random + x
```

#### ECDHE 握手过程

ECDHE 的 TLS 握手也是四次握手，但与 RSA 有关键区别：

- 服务端在发送证书后，还会发送 `Server Key Exchange`，其中包含椭圆曲线参数、服务端椭圆曲线公钥，以及用证书私钥对公钥的签名（常见 RSA 或 ECDSA）；
- 客户端发送 `Client Key Exchange`，其中包含客户端椭圆曲线公钥；
- 客户端可以在第四次握手完成前发送加密的 HTTP 数据，这称为 **TLS False Start**，可以节省一个消息往返。

![ECDHE TLS 握手](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E7%BD%91%E7%BB%9C/https/ech_tls%E6%8F%A1%E6%89%8B.png)

握手过程：

1. **Client Hello**：客户端发送 TLS 版本、密码套件列表、`Client Random`；
2. **Server Hello**：服务端返回 TLS 版本、`Server Random`、选定的密码套件；
3. **Certificate**：服务端发送证书；
4. **Server Key Exchange**：服务端选择椭圆曲线（常见 x25519），生成临时私钥和公钥，并用私钥签名公钥；
5. **Server Hello Done**：服务端信息发送完毕；
6. **Client Key Exchange**：客户端验证证书后，生成临时私钥和公钥，发送客户端公钥；
7. 双方根据 `Client Random`、`Server Random` 和 ECDHE 共享密钥 x 生成会话密钥；
8. **Change Cipher Spec + Finished**：双方验证会话密钥可用，握手完成。

RSA 与 ECDHE 的对比：

| 维度                | RSA 握手           | ECDHE 握手                     |
| ------------------- | ------------------ | ------------------------------ |
| 前向安全            | 不支持             | 支持                           |
| 握手时延            | 通常 2 RTT         | 支持 False Start，可减少 1 RTT |
| Server Key Exchange | 没有               | 有                             |
| 私钥泄漏影响        | 历史密文可能被破解 | 历史密文仍然安全               |

### TLS 记录协议与完整性

TLS 在实现上分为握手协议和记录协议两层：

- **握手协议**：协商加密算法、交换密钥，生成会话密钥；
- **记录协议**：保护应用数据，负责压缩、加密和完整性校验。

TLS 记录协议处理 HTTP 数据的过程：

1. 把消息分割成多个较短的片段；
2. 对每个片段进行压缩；
3. 为片段计算消息认证码（MAC），MAC 通过哈希算法生成，并加入片段序号，用于防止重放攻击；
4. 把压缩片段和 MAC 一起用对称密钥加密；
5. 加上由数据类型、版本号、压缩后长度组成的报头，交给 TCP 传输。

握手协议负责建立安全通道，记录协议负责在通道内保护每一条应用数据。

### HTTPS 优化

HTTPS 的性能消耗主要来自两个环节：

- TLS 握手过程，最长可能花费 2 RTT；
- 握手后的对称加密报文传输。

对称加密算法 AES、ChaCha20 的性能通常不错，部分 CPU 还有硬件加速，因此主要优化空间在 TLS 握手。

![HTTPS 优化提纲](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E7%BD%91%E7%BB%9C/https%E4%BC%98%E5%8C%96/%E4%BC%98%E5%8C%96https%E6%8F%90%E7%BA%B2.png)

**硬件优化**

HTTPS 是计算密集型，主要消耗 CPU，而不是网卡或硬盘。选择计算能力更强的 CPU 可以加速密钥计算。

如果 CPU 支持 AES-NI 指令集，可以优先选择 AES 对称加密，因为 AES-NI 能在指令级别加速 AES。否则可以选择 ChaCha20，它对 CPU 更友好。

**软件优化**

将 Linux 内核、OpenSSL 等软件升级到较新版本，可以获得新特性和性能改进。对大规模服务器集群来说，软件升级涉及时间和风险，需要评估。

**协议优化**

- 用 ECDHE 替代 RSA：支持前向安全，并可通过 False Start 节省 1 RTT；
- 选择性能更好的椭圆曲线，例如 x25519；
- 对称加密可选择 AES-128-GCM，它比 AES-256-GCM 快一些；
- 升级到 TLS 1.3：握手只需 1 RTT，并且只支持安全的密码套件。

TLS 1.3 将 Hello 和公钥交换合并，客户端在 `Client Hello` 中带上支持的椭圆曲线及对应公钥；服务端返回时带上自己的公钥。一个 RTT 后双方即可生成会话密钥。

TLS 1.3 还取消了不支持前向安全的 RSA 密钥传输，密钥交换以 ECDHE 为主；对称加密和签名算法也只保留少量安全套件，降低降级攻击风险。

![TLS 1.2 与 TLS 1.3 握手对比](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E7%BD%91%E7%BB%9C/https%E4%BC%98%E5%8C%96/tls1.2and1.3.png)

**证书优化**

- 证书传输：选择 ECDSA 证书而不是 RSA 证书。相同安全强度下，ECC 密钥长度比 RSA 短，证书更小，传输和验证开销更低；
- 证书验证：使用 OCSP Stapling。服务器定期向 CA 查询证书状态，获得带时间戳和签名的响应并缓存；TLS 握手时把响应发给客户端，客户端不需要再访问 CA。

CRL 是证书吊销列表，由 CA 定期更新。它的问题是实时性差、列表可能很大。OCSP 改为向 CA 实时查询证书状态，解决了 CRL 的实时性问题，但每次查询仍有网络开销。OCSP Stapling 把查询工作交给服务器，减少客户端开销。

### 会话复用

TLS 握手的目的之一是协商会话密钥。会话复用把首次握手协商的密钥缓存起来，再次连接时直接复用，减少完整握手。

**Session ID**

客户端和服务端首次握手后，在内存中缓存会话密钥，并用唯一的 `Session ID` 标识。客户端再次连接时，在 Hello 消息中带上 `Session ID`；服务端查到对应密钥后，直接恢复会话。

缺点是：

- 服务端需要为每个客户端保存会话密钥，客户端越多，内存压力越大；
- 多台服务器通过负载均衡提供服务时，客户端再次连接不一定命中上次的服务器。

**Session Ticket**

服务端不再缓存每个客户端的会话密钥，而是把加密后的会话密钥作为 Ticket 发给客户端缓存。客户端再次连接时发送 Ticket，服务端解密后恢复会话。

集群环境下，需要保证每台服务器加密 Ticket 的密钥一致，这样客户端访问任意一台服务器都能恢复会话。

**Pre-shared Key**

TLS 1.3 支持 Pre-shared Key：重连时客户端把 Ticket 和 HTTP 请求一起发送，达到 0 RTT。

会话复用技术存在安全风险：

- Session ID 和 Session Ticket 不具备前向安全性；加密会话密钥的密钥泄漏，历史密文可能被破解；
- 存在重放攻击风险。中间人可以截获携带 Session ID/Ticket 的请求并重复发送，尤其是会修改数据库的 POST 请求。

应对方式是给会话密钥设置合理过期时间，并只对 GET、HEAD 等安全请求使用会话复用。

### HTTPS 的边界：中间人攻击

HTTPS 本身并不能阻止所有中间人攻击。典型场景是：客户端通过浏览器向服务端发起 HTTPS 请求，被假基站转发到中间人服务器。客户端与中间人完成一次 TLS 握手，中间人再与真正的服务端完成一次 TLS 握手。

后续通信中，中间人用与客户端协商的密钥解密请求，再用与服务端协商的密钥重新加密并转发；响应方向同理。从客户端视角看，请求仍然发往目标域名，但实际上中间人可以读取明文。

这种攻击成立的前提是：客户端接受中间人的证书。中间人发送的伪造证书通常无法通过浏览器校验，浏览器会提示证书存在问题。如果用户执意继续访问，后续 HTTPS 通信就可能被中间人监听。

如果设备被恶意导入了中间人的根证书，操作系统会信任该证书，浏览器可能不再提示风险。此时问题出在客户端环境，而不是 HTTPS 协议本身。

抓包工具能够解密 HTTPS，原理与此相同：抓包工具生成自己的根证书，并让客户端信任它；抓包工具同时作为客户端与服务端通信，从而在中间看到明文。

避免中间人攻击的方式包括：

- 不忽略浏览器的证书错误提示；
- 保持系统环境干净，不安装来源不明的根证书；
- 对安全要求高的场景使用 HTTPS 双向认证，客户端验证服务端，服务端也验证客户端。

## HTTP/2

### HTTP/1.1 的性能问题

现代站点相比早期有几个明显变化：

- 消息变大，从几 KB 到几 MB；
- 页面资源变多，从不到 10 个到超过 100 个；
- 内容形式多样化，包括图片、视频、音频；
- 实时性要求提高。

这些变化放大了 HTTP/1.1 的高延迟问题，主要原因包括：

- **延迟难以下降**：带宽提升后，延迟降到一定程度就很难继续下降；
- **并发连接有限**：浏览器对同一域名通常最多 6 个并发连接，每个连接都要经历 TCP 握手、TLS 握手和慢启动；
- **队头阻塞**：同一连接必须完成一个请求 - 响应事务，才能处理下一个事务；
- **头部巨大且重复**：HTTP 无状态，每个请求都要携带 Header，Cookie 等字段可能很大；
- **不支持服务器推送**：客户端只能通过轮询获取通知，浪费带宽和服务器资源。

HTTP/1.1 的外部优化手段，例如合并图片、Base64 内嵌、打包 JS、分域名，能缓解问题，但无法改变请求 - 响应模型、头部重复、连接握手开销和服务器不能主动推送等限制。要解决这些问题，需要重新设计 HTTP 的传输方式。

### 兼容 HTTP/1.1

HTTP/2 在设计上兼容 HTTP/1.1：

- URI 不变，仍然使用 `http://` 表示明文、`https://` 表示加密；浏览器和服务器在背后自动升级协议；
- 只在应用层改变，仍然基于 TCP；
- 把 HTTP 分解为「语义」和「语法」：语义层与 HTTP/1.1 一致，请求方法、状态码、头字段等规则保留；语法层改为二进制帧。

### 头部压缩：HPACK

HTTP/1.1 的 Header 存在三个问题：

- 固定字段多，例如 Cookie、User-Agent、Accept，可能达到几百甚至上千字节；
- 大量请求和响应中的字段值重复，浪费带宽；
- 字段是 ASCII 编码，便于观察但效率低。

HTTP/2 使用 HPACK 算法压缩头部，包含三部分：

- **静态表**：内置 61 组高频头部字段，不会变化；
- **动态表**：连接双方共同维护，索引从 62 开始，随编码解码更新；
- **Huffman 编码**：对高频字符使用较短编码，压缩字符串。

静态表中的 `Index` 表示索引，`Header Value` 表示索引对应的值，`Header Name` 表示字段名。例如 Index 为 2 代表 GET，Index 为 8 代表状态码 200。

以 `server: nghttpx\r\n` 为例，HTTP/1.1 中算上冒号、空格和末尾的 `\r\n` 共 17 字节；使用静态表和 Huffman 编码后可以压缩到 8 字节，压缩率约 47%。

动态表要求同一个连接上重复传输完全相同的 HTTP 头部。第一次发送某个字段时，双方更新动态表；后续发送时只发送 1 个字节的索引号即可。随着连接上报文增多，动态表积累的字段越来越多，理论上每个头部字段都可以变成 1 字节索引。

动态表会占用内存，Web 服务器通常提供 `http2_max_requests` 之类的配置，限制一个连接上的请求数量，避免动态表无限增大。

### 二进制帧

HTTP/2 把报文改为二进制格式，并划分为帧（Frame）。一条 HTTP 响应通常分为两类帧：

- `HEADERS`：首部；
- `DATA`：消息负载。

![HTTP/1.1 与 HTTP/2 的报文格式](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4@main/%E7%BD%91%E7%BB%9C/http2/%E4%BA%8C%E8%BF%9B%E5%88%B6%E5%B8%A7.png)

二进制编码更紧凑，也便于计算机用位运算解析。例如状态码 200 在 HTTP/1.1 中需要 `'2''0''0'` 三个字符，共 3 字节；HTTP/2 中使用静态表索引加标志位，可以压缩到 1 字节。

HTTP/2 帧头只有 9 字节：

- 前 3 字节：帧数据长度；
- 第 4 字节：帧类型；
- 第 5 字节：标志位，可保存 8 个标志；
- 最后 4 字节：流标识符（Stream ID），最高位保留，实际可用 31 位，最大值约 21 亿。

常见标志位：

- `END_HEADERS`：头数据结束，相当于 HTTP/1 头部后的空行；
- `END_STREAM`：单方向数据发送结束，后续不会再有数据帧；
- `PRIORITY`：流的优先级。

帧数据部分根据帧类型存放不同内容：`HEADERS` 帧存放经过 HPACK 压缩的 HTTP 头部，`DATA` 帧存放 HTTP 包体。

![HTTP/2 帧结构](https://cdn.xiaolincoding.com//picgo/image-20240105143208962.png)

### 并发传输

HTTP/1.1 基于请求 - 响应模型，同一连接必须完成一个事务才能处理下一个事务，因此存在队头阻塞。

HTTP/2 通过 Stream 实现并发：多个 Stream 复用一条 TCP 连接。三个核心概念：

- **Stream**：一个 TCP 连接包含一个或多个 Stream，Stream 是 HTTP/2 并发的关键；
- **Message**：对应 HTTP/1 中的请求或响应，由 HTTP 头部和包体构成；
- **Frame**：HTTP/2 的最小单位，以二进制压缩格式存放 HTTP/1 中的内容。

关系如下：

```text
TCP 连接 → 多个 Stream
Stream → 一个或多个 Message
Message → 一个或多个 Frame
Frame → 可能由多个 TCP 报文承载
```

![Stream、Message 与 Frame](https://cdn.xiaolincoding.com//picgo/image-20240105143224839.png)

不同 Stream 的帧可以乱序发送，因此不同 Stream 可以并发；接收端根据帧头中的 Stream ID 有序组装 HTTP 消息。同一 Stream 内部的帧必须严格有序。

例如服务端可以并行交错地发送 Stream 1 和 Stream 3 的响应，两个 Stream 跑在同一条 TCP 连接上，客户端根据 Stream ID 分别组装。

![HTTP/2 多路复用](https://cdn.xiaolincoding.com/gh/xiaolincoder/network/http/http2%E5%A4%9A%E8%B7%AF%E5%A4%8D%E7%94%A8.jpeg)

客户端和服务端都可以建立 Stream：

- 客户端建立的 Stream 使用奇数号；
- 服务端建立的 Stream 使用偶数号。

同一个连接中的 Stream ID 不能复用，只能顺序递增。Stream ID 耗尽时，需要发送 `GOAWAY` 控制帧关闭 TCP 连接。Nginx 可以通过 `http2_max_concurrent_streams` 设置 Stream 上限，默认 128。

HTTP/2 的并发比 HTTP/1.1 通过多 TCP 连接实现并发更高效：100 个并发 Stream 只需要一次 TCP 连接，而 HTTP/1.1 需要 100 个 TCP 连接，每个连接都要经历握手和慢启动。

HTTP/2 还可以为每个 Stream 设置优先级。例如客户端希望服务器先传 HTML/CSS，再传图片，可以通过设置 Stream 优先级实现。

### 服务器推送

HTTP/1.1 不支持服务器主动推送资源。客户端请求 HTML 后，如果 HTML 依赖 CSS，客户端还要再发起 CSS 请求，需要两次消息往返。

HTTP/2 允许服务端在客户端访问 HTML 时主动推送 CSS，减少消息传递次数。Nginx 配置示例：

```nginx
location /test.html {
  http2_push /test.css;
}
```

服务器推送通过 `PUSH_PROMISE` 帧实现：服务端在帧中传输 HTTP 头部，并通过 `Promised Stream ID` 字段告诉客户端，接下来会在哪个偶数号 Stream 中发送包体。

![HTTP/2 服务器推送](https://cdn.xiaolincoding.com//picgo/image-20240105143315109.png)

### TCP 层的队头阻塞

HTTP/2 通过 Stream 解决了 HTTP 层的队头阻塞，但 TCP 层的队头阻塞仍然存在。

HTTP/2 基于 TCP 传输，TCP 是字节流协议，必须保证收到的字节数据完整且连续。如果序列号较低的 TCP 段丢失，即使后续段已经到达，应用层也无法从内核读取数据，必须等待丢失段重传。

因此，一个 TCP 连接上的所有 HTTP 请求都会被这个丢失的包阻塞。这是 TCP 协议自身的问题，HTTP/2 无法在应用层解决。

## HTTP/3

### HTTP/2 的不足

HTTP/2 通过头部压缩、二进制编码、多路复用、服务器推送提升了性能，但它基于 TCP，存在三个缺陷：

- **队头阻塞**：TCP 丢包时，整个连接上的所有 Stream 都要等待重传；
- **握手延迟**：TCP 三次握手加 TLS 握手（TLS 1.2 为四次握手），最多需要 3 个 RTT，之后还有 TCP 慢启动；
- **连接迁移成本高**：TCP 连接由四元组（源 IP、源端口、目的 IP、目的端口）确定，移动设备从 4G 切换到 WiFi 时 IP 变化，必须重新建立连接。

要解决这些问题，需要替换传输层协议。HTTP/3 选择了 UDP，并在 UDP 之上实现 QUIC。

### QUIC 协议

UDP 简单、不可靠、无序，也不需要在传输层握手。HTTP/3 并不是简单地把 TCP 换成 UDP，而是在 UDP 之上实现 QUIC，由 QUIC 提供类似 TCP 的连接管理、拥塞控制和流量控制。

QUIC 的主要特点：

- **无队头阻塞**：QUIC 也有 Stream 和多路复用，但每个 Stream 独立。某个 Stream 丢包只会阻塞该 Stream，其他 Stream 不受影响；
- **更快的连接建立**：QUIC 内部包含 TLS 1.3，1 个 RTT 即可同时完成连接建立和密钥协商；会话恢复时可以 0 RTT；
- **连接迁移**：QUIC 使用连接 ID 标记通信端点，而不是四元组。IP 或端口变化后，只要连接 ID、TLS 密钥等上下文仍在，就可以复用原连接。

![HTTP/3 与 QUIC](https://cdn.xiaolincoding.com//picgo/image-20240105144308801.png)

QUIC 的可靠性由自身保证：每个数据包都有序号，丢包时由 QUIC 重传。与 HTTP/2 不同，QUIC 的多个 Stream 之间没有依赖关系，某个流丢包不会影响其他流。

HTTP/2 与 QUIC 的队头阻塞对比：

- HTTP/2：一个 TCP 连接上的所有 Stream 共享 TCP 字节流，任一 TCP 段丢失都会阻塞所有 Stream；
- QUIC：每个 Stream 独立，丢包只影响对应 Stream。

### HTTP/3 与 QPACK

HTTP/3 同样采用二进制帧，但帧结构更简单。HTTP/2 的帧头中需要携带 Stream ID，而 HTTP/3 直接使用 QUIC 的 Stream，因此 HTTP/3 帧头只有两个字段：

- 类型；
- 长度。

按帧类型分为数据帧和控制帧，`HEADERS` 帧和 `DATA` 帧属于数据帧。

![HTTP/3 帧结构](https://cdn.xiaolincoding.com//picgo/image-20240105144457456.png)

HTTP/3 的头部压缩算法升级为 QPACK，与 HTTP/2 的 HPACK 类似，也使用静态表、动态表和 Huffman 编码。

主要变化：

- 静态表从 HPACK 的 61 项扩展到 99 项；
- Huffman 编码变化不大；
- 动态表编解码方式不同。

动态表具有时序性：首次出现的请求如果丢包，后续请求可能无法解码 QPACK 头部，因为对方还没有建立对应的动态表。这与 HPACK 的队头阻塞问题类似。

QPACK 通过两个特殊的单向流同步动态表：

- **QPACK Encoder Stream**：编码方把字典（Key-Value）传给对方；
- **QPACK Decoder Stream**：解码方确认字典已更新到本地动态表。

编码方收到解码方的确认后，才使用动态表编码 HTTP 头部。这样避免了动态表更新被丢包阻塞。

## 总结

| 维度       | HTTP/1.1                   | HTTP/2                            | HTTP/3                           |
| ---------- | -------------------------- | --------------------------------- | -------------------------------- |
| 传输层     | TCP                        | TCP                               | UDP + QUIC                       |
| 报文格式   | 文本                       | 二进制帧                          | 二进制帧                         |
| 并发方式   | 多 TCP 连接                | 单 TCP 连接多 Stream              | 单 QUIC 连接多 Stream            |
| 头部压缩   | 无                         | HPACK                             | QPACK                            |
| 队头阻塞   | HTTP 层队头阻塞            | 解决 HTTP 层，仍有 TCP 层队头阻塞 | 各 Stream 独立，无队头阻塞       |
| 服务器推送 | 不支持                     | 支持 `PUSH_PROMISE`               | 支持                             |
| 握手       | TCP + TLS                  | TCP + TLS                         | QUIC 内置 TLS 1.3，1 RTT / 0 RTT |
| 连接迁移   | 四元组绑定，网络变化需重连 | 同 HTTP/1.1                       | 连接 ID，支持迁移                |

HTTP/1.1 的核心问题是请求 - 响应模型、头部重复、并发连接和队头阻塞。HTTP/2 通过二进制帧、HPACK 和 Stream 多路复用解决了 HTTP 层的队头阻塞，但 TCP 层的队头阻塞仍然存在。

HTTP/3 把传输层换成 UDP，并在 QUIC 中实现可靠传输、拥塞控制、流量控制和连接迁移，同时把 TLS 1.3 集成进握手过程。它解决了 TCP 层队头阻塞、握手延迟和连接迁移问题，但也面临 UDP 被部分网络设备丢弃、部署普及缓慢等现实挑战。

## 概述

传输层负责主机中进程之间的通信。IP 层只负责把数据包送到目标主机，不保证交付、顺序和完整性；传输层在 IP 之上提供端到端的通信能力。

传输层有两个主要协议：

- **TCP**：面向连接、可靠、基于字节流，提供重传、排序、流量控制和拥塞控制；
- **UDP**：无连接、不可靠、面向报文，头部只有 8 字节，开销小，适合 DNS、音视频、广播等场景。

TCP 的机制可以分为几条主线：

- 连接生命周期：三次握手、四次挥手、Socket、监听队列；
- 可靠传输：序列号、确认号、重传、滑动窗口、流量控制、拥塞控制；
- 观测与优化：tcpdump/Wireshark、Linux 内核参数、TIME_WAIT 与 Keepalive；
- 异常场景：SYN 丢弃、ISN 随机化、进程崩溃、主机断电、拔网线、队列溢出；
- 协议边界：TCP 的结构性缺陷，以及基于 UDP 的 QUIC 如何补足。

下面按「基础与连接生命周期 → 可靠传输与抓包 → 性能优化 → 异常场景 → TCP 边界与 QUIC」展开。

## 一、TCP 基础与连接生命周期

### TCP 的定义与连接标识

TCP 是**面向连接的、可靠的、基于字节流**的传输层协议。

- **面向连接**：通信前必须建立连接，连接是一对一的；
- **可靠**：通过序列号、确认应答、重传、排序等机制，保证数据无损坏、无间隔、非冗余、按序到达；
- **字节流**：用户消息没有边界，TCP 可能把一条消息拆成多个报文，也可能把多条消息合并成一个报文。

TCP 头部中与连接和可靠性最相关的字段：

- **序列号**：32 位，标识发送方向上的字节编号，用于解决乱序和重复；
- **确认应答号**：32 位，表示下一次期望收到的序列号，用于确认数据已被接收；
- **控制位**：`ACK`、`RST`、`SYN`、`FIN`。

TCP 首部在没有选项时是 20 字节；UDP 首部固定 8 字节。

![TCP 头部格式](https://cdn.xiaolincoding.com//mysql/other/format,png-20230309230534096.png)

RFC 793 把连接定义为：用于保证可靠性和流量控制的某些状态信息的组合，包括 Socket、序列号和窗口大小。

- **Socket**：由 IP 地址和端口号组成；
- **序列号**：用于排序、去重和确认；
- **窗口大小**：用于流量控制。

一个 TCP 连接由**四元组**唯一确定：

```text
源 IP + 源端口 + 目的 IP + 目的端口
```

服务端固定监听一个本地端口时，客户端 IP 和端口可变。IPv4 下客户端 IP 最多 `2^32` 个，端口最多 `2^16` 个，因此单机理论最大连接数约为 `2^48`。实际受文件描述符、内存和 OOM 限制：

- 系统级文件描述符上限：`/proc/sys/fs/file-max`；
- 用户级限制：`/etc/security/limits.conf`；
- 进程级限制：`/proc/sys/fs/nr_open`；
- 每个连接都占用内存，连接过多会触发 OOM。

### TCP 与 UDP 的差异

| 维度      | TCP                          | UDP                      |
| --------- | ---------------------------- | ------------------------ |
| 连接      | 面向连接，先握手             | 无连接，直接发送         |
| 服务对象  | 一对一                       | 一对一、一对多、多对多   |
| 可靠性    | 无差错、不丢失、不重复、按序 | 不保证交付、顺序和完整性 |
| 流量/拥塞 | 都有                         | 都没有                   |
| 首部      | 20 字节起，含选项会变长      | 固定 8 字节              |
| 传输方式  | 字节流，无边界               | 报文，有边界             |
| 分段/分片 | 超过 MSS 在传输层分段        | 超过 MTU 在 IP 层分片    |
| 典型场景  | 文件传输、HTTP/HTTPS         | DNS、SNMP、音视频、广播  |

TCP 适合对可靠性要求高的场景；UDP 适合对实时性要求高、能容忍少量丢包的场景。UDP 之上也可以实现可靠传输，QUIC 就是典型例子。

### 三次握手

TCP 建立连接通过三次握手完成：

![TCP 三次握手](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost4/%E7%BD%91%E7%BB%9C/TCP%E4%B8%89%E6%AC%A1%E6%8F%A1%E6%89%8B.drawio.png)

1. **第一次握手**：客户端随机生成初始序列号 `client_isn`，把 `SYN` 置为 1，发送 SYN 报文，进入 `SYN_SENT` 状态；
2. **第二次握手**：服务端随机生成 `server_isn`，把 `SYN` 和 `ACK` 置为 1，确认号为 `client_isn + 1`，发送 SYN-ACK 报文，进入 `SYN_RCVD` 状态；
3. **第三次握手**：客户端把 `ACK` 置为 1，确认号为 `server_isn + 1`，发送 ACK 报文，进入 `ESTABLISHED` 状态；服务端收到后也进入 `ESTABLISHED`。

第三次握手可以携带数据，前两次握手不能携带应用层数据。

`connect()` 在第二次握手后返回；服务端 `accept()` 在三次握手完成后，从全连接队列取出连接时返回。

#### 三次握手的必要性

三次握手有三个目的：

- **防止历史连接初始化**：客户端先发送旧 SYN（seq=90），网络阻塞后又发送新 SYN（seq=100）。旧 SYN 先到，服务端回 `ack=91`；客户端期望 `101`，于是回 RST，服务端释放旧连接，新 SYN 再正常建立连接。两次握手时，服务端收到 SYN 就进入 `ESTABLISHED`，无法在发送数据前阻止历史连接，会浪费资源。
- **同步双方初始序列号**：双方都需要确认对方的 ISN 已被接收。四次握手也能做到，但第二次和第三次可以合并，因此三次握手是最少可靠次数。
- **避免资源浪费**：两次握手下，客户端重复发送 SYN，服务端每收到一个就建立一个连接，会产生大量无效连接。

#### 握手丢包与重传

- **第一次 SYN 丢失**：客户端超时重传 SYN，序列号不变。Linux `tcp_syn_retries` 默认 5，RTO 按 1、2、4、8、16 秒翻倍，最后再等 32 秒，总耗时约 63 秒。
- **第二次 SYN-ACK 丢失**：客户端重传 SYN，服务端重传 SYN-ACK。重传次数分别由 `tcp_syn_retries` 和 `tcp_synack_retries` 控制，默认都是 5。
- **第三次 ACK 丢失**：ACK 不重传；服务端收不到 ACK，会重传 SYN-ACK，直到收到 ACK 或达到 `tcp_synack_retries` 上限。

#### MSS 与 IP 分片

- **MTU**：一个网络包的最大长度，以太网通常为 1500 字节；
- **MSS**：去掉 IP 和 TCP 头部后，一个网络包能容纳的 TCP 数据最大长度。

如果 TCP 报文交给 IP 层分片，任意一个 IP 分片丢失，接收方 IP 层无法组装完整 TCP 报文，发送方需要重传整个 TCP 报文。因此 TCP 在握手时协商 MSS，由 TCP 层按 MSS 分片；某个 TCP 分片丢失时，只重传对应分片。

### 四次挥手

TCP 断开连接通过四次挥手完成：

![TCP 四次挥手](https://cdn.xiaolincoding.com//mysql/other/format,png-20230309230614791.png)

1. 主动关闭方发送 `FIN`，进入 `FIN_WAIT_1`；
2. 被动关闭方回 `ACK`，进入 `CLOSE_WAIT`；
3. 主动关闭方收到 `ACK`，进入 `FIN_WAIT_2`；
4. 被动关闭方处理完数据后发送 `FIN`，进入 `LAST_ACK`；
5. 主动关闭方回 `ACK`，进入 `TIME_WAIT`；
6. 被动关闭方收到 `ACK` 后进入 `CLOSE`；
7. 主动关闭方等待 `2MSL` 后进入 `CLOSE`。

只有主动关闭方才有 `TIME_WAIT` 状态。

#### 四次挥手的必要性

关闭连接时，主动方发送 `FIN` 只表示自己不再发送数据，但仍可以接收数据。被动方收到 `FIN` 后先回 `ACK`，因为可能还有数据要发送；等数据发送完毕，才发送自己的 `FIN`。因此 `ACK` 和 `FIN` 通常分开发送，形成四次挥手。

在特定情况下，四次挥手可以变成三次：被动方没有数据要发送，并且开启了 TCP 延迟确认，那么第二次 `ACK` 和第三次 `FIN` 可以合并。

`close()` 会同时关闭读写方向；`shutdown()` 可以只关闭一个方向。`SHUT_WR` 表示半关闭，属于优雅关闭；`SHUT_RD` 不会发送 FIN。

#### TIME_WAIT 与 2MSL

`TIME_WAIT` 持续 `2MSL`，Linux 默认 `MSL=30s`，因此 `TIME_WAIT` 约 60 秒。

`TIME_WAIT` 有两个作用：

- **防止历史数据被新连接误收**：旧连接延迟的数据包如果在新连接建立后到达，序列号可能落在新连接接收窗口内；等待 2MSL 可以让旧数据包在网络中自然消失；
- **保证被动方正常关闭**：主动方最后一次 ACK 丢失时，被动方会重传 FIN；如果主动方已经进入 `CLOSE`，收到 FIN 会回 RST，被动方会看到 `Connection reset by peer`。`TIME_WAIT` 让主动方还能重发 ACK。

`2MSL` 从主动方收到 FIN 并发送 ACK 开始计时；期间再次收到 FIN，计时器重置。

#### 挥手丢包与状态处理

- 第一次 FIN 丢失：主动方超时重传 FIN，重传次数由 `tcp_orphan_retries` 控制；
- 第二次 ACK 丢失：ACK 不重传，主动方重传 FIN；
- 第三次 FIN 丢失：被动方重传 FIN，次数同样由 `tcp_orphan_retries` 控制；
- 第四次 ACK 丢失：被动方在 `LAST_ACK` 重传 FIN；主动方在 `TIME_WAIT` 收到 FIN 后重置 2MSL。

对于 `close()` 关闭的孤儿连接，`FIN_WAIT_2` 受 `tcp_fin_timeout` 控制，默认 60 秒；`shutdown()` 关闭的半关闭连接不受该参数限制，可能长期停留在 `FIN_WAIT_2`。

### Socket、监听队列与 accept

TCP Socket 编程的基本流程：

![TCP Socket 编程流程](https://cdn.xiaolincoding.com//mysql/other/format,png-20230309230545997.png)

- 服务端和客户端初始化 `socket`，得到文件描述符；
- 服务端 `bind` 绑定 IP 和端口；
- 服务端 `listen` 监听；
- 服务端 `accept` 等待客户端连接；
- 客户端 `connect` 发起连接；
- `accept` 返回已完成连接的 socket；
- 双方通过 `read`/`write` 读写数据；
- 客户端 `close` 后，服务端 `read` 读到 EOF，处理完数据后 `close`。

监听 socket 和已完成连接 socket 是两个不同的 socket。前者只负责接收新连接，后者用于实际数据传输。

#### 半连接队列与全连接队列

Linux 内核维护两个队列：

- **半连接队列（SYN 队列）**：收到 SYN 后，连接处于 `SYN_RCVD`，放入 SYN 队列；
- **全连接队列（accept 队列）**：三次握手完成后，连接进入 `ESTABLISHED`，放入 accept 队列，等待应用调用 `accept()`。

![SYN 队列与 accept 队列](https://cdn.xiaolincoding.com//mysql/other/format,png-20230309230542373.png)

`listen(int socketfd, int backlog)` 的 `backlog` 在 Linux 2.2 之后表示 accept 队列长度，但上限是 `somaxconn`：

```text
accept 队列长度 = min(backlog, somaxconn)
```

`somaxconn` 默认 128；Nginx、Tomcat 等 Web 服务的 `backlog` 默认常见为 511。`ss -lnt` 中，LISTEN 状态的 `Recv-Q` 是当前 accept 队列长度，`Send-Q` 是最大长度。

队列溢出时：

- 半连接队列满：默认丢弃新的 SYN；开启 `tcp_syncookies=1` 后可以绕过半连接队列；
- 全连接队列满：`tcp_abort_on_overflow=0` 时丢弃第三次 ACK，让客户端重传；`=1` 时直接回 RST。生产环境通常建议 0，以承受突发流量。

`accept()` 不参与三次握手，只负责从全连接队列取连接。因此没有 `accept()`，三次握手仍可完成；但没有 `listen()`，服务端收到 SYN 会回 RST。TCP 自连接和 TCP 同时打开是例外，它们不需要服务端 `listen`。

### 字节流与粘包

UDP 是面向报文的：操作系统不会拆分用户消息，一个 UDP 报文就是一个消息边界，`recvfrom()` 一次取一个报文。

TCP 是面向字节流的：`send()` 只是把数据拷贝到内核发送缓冲区，具体何时发送、拆成几个 TCP 报文，由发送窗口、拥塞窗口、缓冲区等因素决定。因此：

- 一条用户消息可能被拆成多个 TCP 报文；
- 多条用户消息可能被合并到一个 TCP 报文；
- 接收方不能假设“一次 `read` 对应一条消息”。

所谓“粘包”，本质是应用层不知道消息边界。常见解决方式：

- **固定长度**：每个消息固定 N 字节，不足补齐；
- **特殊分隔符**：例如 HTTP 用 CRLF 分隔头部，消息内容中出现分隔符时需要转义；
- **长度字段**：消息头部先放 4 字节长度，再放消息体。

```c
struct message {
    uint32_t message_length;
    char message_data[];
};
```

接收方先读 4 字节长度，再按长度读取消息体。

### 序列号与确认号的变化

TCP 序列号和确认号遵循两条规则：

```text
发送报文的 seq = 上一次发送的 seq + len
若上一次发送的是 SYN 或 FIN，则额外 +1

发送报文的 ack = 上一次收到的报文 seq + len
若收到的是 SYN 或 FIN，则额外 +1
```

SYN 和 FIN 各消耗一个序列号。

三次握手中的变化：

- 客户端 SYN：`seq = client_isn`；
- 服务端 SYN-ACK：`seq = server_isn`，`ack = client_isn + 1`；
- 客户端 ACK：`seq = client_isn + 1`，`ack = server_isn + 1`。

数据传输示例：客户端发送 10 字节数据，`seq = client_isn + 1`，`ack = server_isn + 1`；服务端确认时 `ack = client_isn + 11`。

四次挥手中的变化：

- 客户端 FIN：`seq = client_isn + 11`，`ack = server_isn + 1`；
- 服务端 ACK/FIN：`seq = server_isn + 1`，`ack = client_isn + 12`；
- 客户端最后 ACK：`seq = client_isn + 12`，`ack = server_isn + 2`。

如果第三次握手的 ACK 丢失，客户端发送的第一个数据报文会带有 ACK 标志，其 seq/ack 与第三次握手相同；处于 `SYN_RCVD` 的服务端可以据此完成连接建立并接收数据。

## 二、TCP 的可靠传输

### 重传机制

TCP 通过序列号和确认应答实现可靠传输。数据丢失时，主要有四种重传机制。

#### 超时重传

发送数据时设置定时器，超过时间没有收到 ACK 就重发。两种场景会触发超时重传：

- 数据包丢失；
- 确认应答丢失。

超时时间由 `RTO`（Retransmission Timeout）表示。`RTO` 应略大于 `RTT`（Round-Trip Time）：

- `RTO` 太大：丢包后重发慢，效率低；
- `RTO` 太小：没有丢包也重发，增加网络拥塞，导致更多超时和重发。

`RTT` 会随网络变化，因此 `RTO` 是动态值。TCP 采样 RTT 并计算平滑 RTT 和 RTT 波动范围；Linux 使用 `α=0.125`、`β=0.25`、`μ=1`、`∂=4` 等参数。连续超时重传时，`RTO` 按指数翻倍。

#### 快速重传

快速重传不以时间为驱动，而以数据为驱动：发送方收到**三个相同的 ACK** 时，判断对应报文丢失，在定时器过期前立即重传。

例如发送 Seq1~Seq5，Seq2 丢失：

- Seq1 到达，接收方回 ACK 2；
- Seq3、Seq4、Seq5 到达，接收方仍回 ACK 2；
- 发送方收到三个 ACK 2，重传 Seq2；
- Seq2 到达后，接收方回 ACK 6。

快速重传只解决超时等待问题，但无法确定“只重传丢失的一个，还是重传之后所有已发送报文”。如果只重传一个，后续丢失报文还要等更多重复 ACK；如果重传之后所有报文，又会重复发送已收到的数据。

![快速重传](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C/TCP-%E5%8F%AF%E9%9D%A0%E7%89%B9%E6%80%A7/10.jpg)

#### SACK

SACK（Selective Acknowledgment，选择性确认）在 TCP 选项字段中携带已收到的数据范围，发送方据此只重传缺失的数据。

Linux 通过 `net.ipv4.tcp_sack` 开启，2.4 之后默认开启，需要双方都支持。

#### D-SACK

D-SACK（Duplicate SACK）用 SACK 告诉发送方哪些数据被重复接收。典型场景：

- ACK 丢失：发送方超时重传，接收方发现数据重复，回 SACK 说明重复范围；
- 网络延迟：延迟数据包在快速重传后到达，接收方回 SACK 说明重复。

D-SACK 可以判断是数据丢失、ACK 丢失、网络延迟还是网络复制。`net.ipv4.tcp_dsack` 默认开启。

### 滑动窗口

如果每发一个数据包都等一个 ACK，往返时间越长，效率越低。TCP 引入**窗口**：无需等待确认应答，可以连续发送的数据最大值。

窗口是操作系统开辟的缓存空间。发送方在收到 ACK 前必须保留已发送数据；收到 ACK 后，才能从缓存中清除。

窗口使用**累计确认**：ACK 700 表示 700 之前的所有数据都已收到。即使 ACK 600 丢失，收到 ACK 700 也能确认之前的数据。

![滑动窗口并行传输](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C/TCP-%E5%8F%AF%E9%9D%A0%E7%89%B9%E6%80%A7/15.jpg)

#### 发送方窗口

发送方缓存分为四个区域：

1. 已发送并收到 ACK；
2. 已发送但未收到 ACK；
3. 未发送，但在接收方处理范围内；
4. 未发送，且超过接收方处理范围。

三个关键指针：

- `SND.WND`：发送窗口大小，由接收方指定；
- `SND.UNA`：已发送但未确认的第一个字节；
- `SND.NXT`：未发送但可发送范围的第一个字节。

可用窗口大小：

```text
可用窗口 = SND.WND - (SND.NXT - SND.UNA)
```

#### 接收方窗口

接收方窗口分为三部分：

- 已成功接收并确认的数据，等待应用读取；
- 未收到但可以接收的数据；
- 未收到且不可接收的数据。

关键字段：

- `RCV.WND`：接收窗口大小，会通告给发送方；
- `RCV.NXT`：期望收到的下一个字节序列号。

接收窗口和发送窗口约等于，但不完全相等，因为窗口通告存在网络时延。

### 流量控制

流量控制让发送方根据接收方的实际接收能力控制发送量，避免发送方发得太快导致接收方处理不过来。

接收方通过 TCP 头部的 `Window` 字段通告可用窗口。发送方发送的数据不能超过接收方窗口。

#### 操作系统缓冲区的影响

发送窗口和接收窗口的数据都存放在操作系统内存缓冲区中，缓冲区会被操作系统动态调整。

- 应用读取慢：接收窗口收缩，发送窗口随之减小；
- 窗口收缩到 0：发送方停止发送，形成**窗口关闭**；
- 如果先减少缓存再收缩窗口，发送方可能按旧窗口发送超出新窗口的数据，导致丢包。TCP 规定先收缩窗口，过一段时间再减少缓存。

#### 窗口关闭与窗口探测

窗口为 0 时，发送方停止发送。接收方处理完数据后，会发送窗口非 0 的 ACK；如果该 ACK 丢失，双方会互相等待，形成死锁。

TCP 使用持续定时器：收到零窗口通知后启动定时器，超时发送**窗口探测**报文，接收方在确认中给出当前窗口大小。

- 窗口仍为 0：重新启动定时器；
- 窗口非 0：死锁解除。

窗口探测一般 3 次，每次约 30–60 秒；仍为 0 时，部分实现会发 RST 断开连接。

#### 糊涂窗口综合症

如果接收方通告很小的窗口，发送方就发送很小的数据，会导致大量小包，效率很低。TCP + IP 头部共 40 字节，为几个字节数据付出这么大开销不划算。

解决需要双方配合：

- **接收方**：窗口小于 `min(MSS, 缓存空间/2)` 时通告 0，等窗口大于等于 MSS 或缓存空出一半再打开；
- **发送方**：使用 Nagle 算法，满足“窗口 >= MSS 且数据 >= MSS”或“收到之前数据的 ACK”才发送。

Nagle 算法默认开启。交互性强的程序（如 SSH、telnet）可以通过 `TCP_NODELAY` 关闭：

```c
setsockopt(sock_fd, IPPROTO_TCP, TCP_NODELAY, (char *)&value, sizeof(int));
```

如果接收方仍然通告小窗口，仅开启 Nagle 也无法完全避免糊涂窗口综合症。

### 拥塞控制

流量控制关注接收方能力，拥塞控制关注网络状况。网络拥塞时继续发送大量数据，会导致时延、丢包和重传，进一步加重拥塞。

发送方维护**拥塞窗口** `cwnd`，实际发送窗口为：

```text
swnd = min(cwnd, rwnd)
```

没有拥塞时 `cwnd` 增大，出现拥塞时 `cwnd` 减小。发送方超时重传时，认为网络出现拥塞。

拥塞控制包括四个算法：慢启动、拥塞避免、拥塞发生、快速恢复。

![慢启动与拥塞控制](https://cdn.xiaolincoding.com/gh/xiaolincoder/ImageHost2/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C/TCP-%E5%8F%AF%E9%9D%A0%E7%89%B9%E6%80%A7/27.jpg)

#### 慢启动

连接建立后，`cwnd` 从较小值开始，每收到一个 ACK 就加 1，呈指数增长。

- 初始 `cwnd = 1` 个 MSS；
- 收到 1 个 ACK，`cwnd` 变 2，可发 2 个；
- 收到 2 个 ACK，`cwnd` 变 4，可发 4 个；
- 以此类推。

慢启动门限 `ssthresh` 决定何时切换到拥塞避免：

- `cwnd < ssthresh`：慢启动；
- `cwnd >= ssthresh`：拥塞避免。

#### 拥塞避免

每收到一个 ACK，`cwnd` 增加 `1/cwnd`，从指数增长变为线性增长。`ssthresh` 常见值为 65535 字节。

#### 拥塞发生

**超时重传**：

```text
ssthresh = cwnd / 2
cwnd = 1
```

然后重新进入慢启动。Linux 每个 TCP 连接的 `cwnd` 初始值通常为 10 个 MSS，可用 `ss -nli` 查看。

**快速重传**：

```text
cwnd = cwnd / 2
ssthresh = cwnd
```

然后进入快速恢复。

#### 快速恢复

快速恢复认为还能收到三个重复 ACK，说明网络没有完全崩溃，不必像超时重传那样回到 `cwnd=1`：

- `cwnd = ssthresh + 3`；
- 重传丢失的数据包；
- 再收到重复 ACK，`cwnd` 加 1；
- 收到新数据的 ACK 后，`cwnd = ssthresh`，进入拥塞避免。

### 抓包分析

tcpdump 和 Wireshark 是分析 TCP 的常用工具：

- **tcpdump**：命令行抓包，适合 Linux 服务器；
- **Wireshark**：可视化分析，适合查看协议栈各层字段和时序图。

常见用法：

```bash
tcpdump -i eth0 -nn tcp and port 80 -s0 -w http.pcap
```

Wireshark 默认显示相对序列号；取消 `Relative Seq` 后才能看到真实 ISN。

#### 握手与挥手抓包

一次 HTTP 请求的抓包通常包含：

- 前 3 个包：TCP 三次握手；
- 中间：HTTP 请求和响应；
- 最后 3 或 4 个包：TCP 挥手。

抓包中常见三次挥手，原因是被动方没有数据要发送，并且开启了 TCP 延迟确认，第二次 ACK 和第三次 FIN 合并。

#### 握手丢包实验

- **第一次 SYN 丢失**：SYN 重传 5 次，抓包时间约为 1、3、7、15、31 秒，RTO 指数翻倍；总耗时约 63 秒。
- **第二次 SYN-ACK 丢失**：客户端重传 SYN，服务端重传 SYN-ACK；重传次数分别由 `tcp_syn_retries` 和 `tcp_synack_retries` 控制。
- **第三次 ACK 丢失**：服务端停留在 `SYN_RCVD`，重传 SYN-ACK；客户端已进入 `ESTABLISHED`，但发送数据后可能重传多次才断开。

#### TFO 抓包

TCP Fast Open（TFO）允许在 SYN 中携带应用数据：

- 首次连接：客户端请求 TFO Cookie，服务端在 SYN-ACK 中下发；
- 后续连接：客户端在 SYN 中携带 Cookie 和数据，服务端在握手完成前即可处理请求。

Linux 通过 `tcp_fastopen` 控制：0 关闭、1 客户端、2 服务端、3 双向。

#### 快速重传与窗口

Wireshark 中的“快速重传”“重复 ACK”是分析工具根据报文推断的标记，不是 TCP 报文本身的字段。SACK 存在时，发送方可以只重传缺失段。

窗口缩放因子在三次握手中协商：

```text
实际窗口 = Window size value × Window size scaling factor
```

抓包中的窗口是接收方通告值，发送方实际发送窗口还要受拥塞窗口限制。

#### 延迟确认与 Nagle

- **延迟确认**：接收方不立即回 ACK，而是等待一小段时间，希望把多个 ACK 合并；Linux 在 `HZ=1000` 时最大约 200ms，最小约 40ms。
- **Nagle**：发送方把小数据缓存起来，等待更多数据或 ACK 再发送。

Nagle 和延迟确认同时开启时，可能互相等待，最坏每个包多出约 200ms。交互性强的应用通常关闭 Nagle，或使用 `TCP_QUICKACK` 关闭延迟确认。

## 三、性能优化与参数

### 握手优化

**客户端**：

- `tcp_syn_retries` 控制 SYN 重传次数，默认 5。内网环境可以适当调低，让连接失败更快暴露。

**服务端**：

- 半连接队列溢出可以通过 `netstat -s` 中的 `SYNs to LISTEN sockets dropped` 观察；
- 增大半连接队列需要同时调整 `tcp_max_syn_backlog`、`somaxconn` 和 `listen()` 的 backlog；
- 开启 `tcp_syncookies=1`，在队列满时绕过半连接队列；
- `tcp_synack_retries` 控制 SYN-ACK 重传次数，默认 5。

**accept 队列**：

- 上限为 `min(backlog, somaxconn)`；
- `ss -ltn` 可查看当前队列长度；
- `tcp_abort_on_overflow=0` 丢 ACK，适合承受突发；`=1` 回 RST，适合长期溢出时快速失败。

### 四次挥手优化与 TIME_WAIT

**close 与 shutdown**：

- `close()` 同时关闭读写，多个进程共享 socket 时只减少引用计数，计数为 0 才发 FIN；
- `shutdown(SHUT_WR)` 只关闭写方向，属于半关闭；`SHUT_RD` 不发 FIN。

**FIN_WAIT_1**：

- FIN 重传由 `tcp_orphan_retries` 控制；
- `tcp_max_orphans` 限制孤儿连接数量，超出可能直接回 RST。

**FIN_WAIT_2**：

- `close()` 的孤儿连接受 `tcp_fin_timeout` 控制，默认 60 秒；
- `shutdown()` 的半关闭连接不受该参数限制。

**TIME_WAIT**：

- Linux 默认持续 60 秒；
- `tcp_max_tw_buckets` 限制 TIME_WAIT 数量，默认 18000，超出会重置；
- `tcp_tw_reuse=1` 允许客户端复用 TIME_WAIT 超过 1 秒的连接，但需要 `tcp_timestamps=1`；
- `tcp_tw_recycle` 在 NAT 环境下会因 per-host PAWS 丢弃 SYN，Linux 4.12 已移除；
- `SO_LINGER(l_onoff=1, l_linger=0)` 会在 close 时直接发 RST，跳过四次挥手和 TIME_WAIT，属于危险操作。

`tcp_tw_reuse` 默认关闭，原因是复用 TIME_WAIT 可能带来两类问题：

- 延迟的 RST 被 PAWS 放行，可能断开新连接；
- 第四次挥手 ACK 丢失时，服务端重传 FIN，可能与新连接的 SYN 冲突。

`tcp_rfc1337` 控制 TIME_WAIT 收到 RST 的行为：0 提前释放，1 丢弃 RST。对安全性要求高的场景可以设为 1。

### 数据传输优化

**带宽时延积**：

```text
BDP = 带宽 × RTT
```

例如带宽 100MB/s、RTT 10ms，BDP 为 1MB。发送缓冲区应接近 BDP：太小跑不满带宽，太大可能造成排队和丢包。

**窗口扩大**：

TCP 窗口字段 16 位，最大 65535 字节（64KB）。窗口扩大选项使用 14 位因子，最大窗口为 `2^16 × 2^14 = 2^30` 字节，即 1GB。`tcp_window_scaling=1` 默认开启，需要双方在 SYN 中都带选项。

**缓冲区参数**：

```text
net.ipv4.tcp_wmem = 4096 16384 4194304
net.ipv4.tcp_rmem = 4096 87380 6291456
```

三个值分别是 min、default、max。

- `tcp_moderate_rcvbuf=1`：接收缓冲区自动调节；
- `tcp_mem`：以页为单位控制 TCP 整体内存，超过第三阈值时新连接可能无法分配内存；
- 不建议在 socket 上设置 `SO_SNDBUF`/`SO_RCVBUF`，会关闭自动调节。

### TCP Keepalive 与 HTTP Keep-Alive

两者名字相似，但不是同一个机制：

- **HTTP Keep-Alive**：应用层长连接，让多个 HTTP 请求复用同一个 TCP 连接；
- **TCP Keepalive**：TCP 层保活探测，在没有数据交互时检测对端是否存活。

HTTP/1.0 默认关闭 Keep-Alive，需要 `Connection: Keep-Alive`；HTTP/1.1 默认开启，`Connection: close` 关闭。Web 服务通过 `keepalive_timeout` 控制空闲长连接的超时时间，通过 `keepalive_requests` 控制单连接最大请求数。

TCP Keepalive 参数：

```text
net.ipv4.tcp_keepalive_time = 7200
net.ipv4.tcp_keepalive_intvl = 75
net.ipv4.tcp_keepalive_probes = 9
```

Linux 默认最少需要 2 小时 11 分 15 秒才能发现死亡连接。应用需要设置 `SO_KEEPALIVE` 才能启用。

### TFO 与 TLS 1.3

常规 HTTPS 需要先完成 TCP 三次握手，再进行 TLS 握手：

- TLS 1.2 约 2 RTT；
- TLS 1.3 约 1 RTT；
- TLS 1.3 会话恢复可以 0 RTT。

TCP 和 TLS 能否同时握手，取决于两个条件：

- 双方都支持 TFO；
- 使用 TLS 1.3，并且双方已经完成过一次通信。

TFO 首次连接仍然正常握手并缓存 Cookie；后续 SYN 可以携带应用数据，服务端在握手完成前即可处理，从而与 TLS 握手重叠，节省 1 RTT。

## 四、异常场景与排查

### ISN 随机化

TCP 每次建立连接都会生成不同的初始序列号，原因有两个：

- 防止历史报文被下一个相同四元组的连接接收；
- 提高安全性，增加伪造序列号的难度。

ISN 生成算法：

```text
ISN = M + F(localhost, localport, remotehost, remoteport)
```

- `M` 是计时器，每 4 微秒加 1；
- `F` 是根据四元组生成的 Hash 值。

`M` 回绕一次约 4.55 小时。如果 ISN 固定，旧连接延迟的数据包可能正好落在新连接接收窗口内，造成数据错乱。ISN 随机化只能大概率避免，序列号回绕仍可能发生，需要时间戳 PAWS 兜底。

### SYN 报文被丢弃的常见场景

**tcp_tw_recycle 与 NAT**

`tcp_tw_recycle` 与 `tcp_timestamps` 同时开启时，会启用 per-host PAWS：按对端 IP 检查时间戳。NAT 后多台客户端共享同一个 IP，如果某台客户端的 timestamp 较小，服务端会丢弃它的 SYN。

`tcp_tw_recycle` 在 Linux 4.12 已被移除，现代系统不应再依赖该参数。

**队列溢出**

- 半连接队列满：默认丢弃新的 SYN；开启 `tcp_syncookies=1` 可以绕过；
- 全连接队列满：`tcp_abort_on_overflow=0` 丢 ACK，`=1` 回 RST；
- `ss -lnt` 中 `Recv-Q > Send-Q` 说明 accept 队列已满；
- `netstat -s` 可以查看 `overflowed` 和 `SYNs to LISTEN sockets dropped`。

### 已建立连接收到 SYN

**不同源端口**：视为新连接，正常三次握手。旧连接如果服务端发数据，客户端会回 RST；如果服务端不发数据，旧连接可能一直保持到保活超时。

**相同源端口**：服务端回 **Challenge ACK**，其中携带正确的 seq/ack，而不是确认新的 SYN。客户端发现 ack 不是期望值，回 RST，服务端释放旧连接。

精确杀死 TCP 连接需要伪造 RST，条件是四元组相同且 seq 落在对方接收窗口内。`killcx` 会先发 SYN 获取 Challenge ACK，再伪造 RST；`tcpkill` 只能被动嗅探活跃连接。

### 乱序 FIN 与 TIME_WAIT 收到 SYN

**乱序 FIN**：`FIN_WAIT_2` 收到乱序 FIN 时，不会立即进入 `TIME_WAIT`。FIN 会放入乱序队列，等缺失的数据补齐、序列号连续后，才调用 `tcp_fin`，发送 ACK 并进入 `TIME_WAIT`。

**TIME_WAIT 收到 SYN**：是否重建连接取决于 SYN 是否合法。

开启时间戳时，合法条件通常是：

- SYN 的 seq 大于服务端 `rcv_nxt`；
- SYN 的 timestamp 大于 `ts_recent`。

合法：复用四元组，跳过 2MSL，进入 `SYN_RCVD` 继续建连；
非法：服务端回一个与第四次挥手相同的 ACK，客户端发现 ack 不是期望值，回 RST。

未开启时间戳时，只根据 seq 判断。

### 主机崩溃、进程崩溃与拔网线

**进程崩溃**：内核回收进程的 TCP 连接资源，会发送 FIN，仍能完成四次挥手；`kill -9` 也能触发 FIN。

**主机崩溃**：服务端无法感知，连接会一直处于 `ESTABLISHED`，直到服务端重启进程。

**有数据传输时**：客户端宕机后快速重启，收到旧连接的重传报文，由于没有进程绑定端口或找不到 socket，会回 RST；如果客户端一直不重启，服务端重传达到 `tcp_retries2` 阈值后断开。

`tcp_retries2=15` 时，内核按值计算的 timeout 约为 924.6 秒；实际重传次数受 RTO 和 timeout 共同影响，不一定恰好 15 次。

**拔掉网线**：TCP 连接状态在内核中不会因为物理断网立即改变，连接仍显示 `ESTABLISHED`。

- 有数据传输：发送方超时重传；插回网线后可以恢复；未插回则达到重传上限后断开；
- 无数据传输：未开启 Keepalive 时连接一直保持；开启 Keepalive 时按 7200/75/9 参数探测，约 2 小时 11 分 15 秒发现死亡。

### 大量 TIME_WAIT 与 CLOSE_WAIT

**服务端大量 TIME_WAIT**：说明服务端主动关闭了大量连接，常见原因：

- HTTP 没有使用长连接；
- HTTP 长连接超时，例如 Nginx `keepalive_timeout`；
- HTTP 长连接请求数达到上限，例如 Nginx `keepalive_requests` 默认 100。

**大量 CLOSE_WAIT**：说明被动关闭方没有调用 `close()`。常见原因：

- 监听 socket 没有注册到 epoll；
- 新连接到来时没有 `accept()`；
- `accept()` 后没有把连接注册到 epoll；
- 收到 FIN 后代码没有执行 `close()`。

CLOSE_WAIT 通常不是内核参数问题，而是应用代码问题。

### TCP 不保证应用层不丢数据

TCP 只保证传输层到传输层的可靠交付，不保证应用层消息一定不丢。

数据发送路径：

```text
用户空间 → 内核发送缓冲区 → 传输层/网络层 → qdisc → 网卡 RingBuffer
→ 网络 → 目的网卡 RingBuffer → 硬中断 → 软中断 → 内核接收缓冲区 → 用户空间
```

任一环节都可能丢包：

- 建连阶段：半连接/全连接队列满；
- 发送阶段：qdisc 队列满，`txqueuelen` 默认 1000；
- 网卡 RingBuffer 满：`ethtool -S` 查看 `rx_queue_0_drops`；
- 接收缓冲区满：窗口变为 0，继续发送会丢；
- 链路丢包：`ping`、`mtr` 查看端到端和逐跳丢包；
- 应用读取前进程崩溃：内核缓冲区中的数据仍会丢失。

因此，需要应用层确认、消息 ID、重试和对账机制，不能仅依赖 TCP。

## 五、TCP 的边界、QUIC 与端口

### TCP 的结构性缺陷

TCP 有四个结构性问题：

- **升级困难**：TCP 实现在内核中，升级需要更新内核并回归测试；TFO 等扩展在部分系统上支持有限；
- **建立连接延迟**：TCP 1 RTT + TLS 1.2 约 2 RTT，总计约 3 RTT；TLS 在应用层、TCP 在内核，难以合并握手；
- **队头阻塞**：TCP 是字节流，必须按序交付；一个 TCP 段丢失，后续数据即使到达也不能交给应用层。HTTP/2 多流复用一条 TCP 连接时，一个丢包会阻塞所有流；
- **网络迁移成本高**：TCP 连接由四元组确定，移动设备从 4G 切换到 WiFi 时 IP 变化，必须重新建立连接，重新握手、TLS 和慢启动。

此外，TCP 头部不加密，序列号明文传输；伪造 RST 只需要序列号落在接收窗口内。三次握手同步 ISN 和随机化提高了猜测难度，但不能防止中途截获后的伪造。

### QUIC 如何基于 UDP 实现可靠传输

QUIC 在 UDP 之上实现可靠传输，同时吸收 TLS 1.3，主要设计如下。

**分层结构**：

```text
UDP → Packet Header → QUIC Frame Header → HTTP 消息
```

- Long Packet Header：首次建立连接；
- Short Packet Header：日常传输；
- 连接 ID：支持连接迁移。

**Packet Number**：严格递增，重传的数据包也使用更大的编号。这样可以避免 TCP 重传的 RTT 采样歧义，并支持乱序确认，丢包不会阻塞窗口右移。

**Frame**：每个 Frame 携带 Stream ID 和 Offset：

- Stream ID 区分并发 HTTP 流；
- Offset 类似 TCP 序列号，保证流内顺序和可靠；
- Stream ID + Offset 相同即同一数据，即使 Packet Number 不同。

**无队头阻塞**：TCP 接收窗口只在有序数据到达时滑动，HTTP/2 多个 Stream 共用一条 TCP 窗口，一个丢包会阻塞所有 Stream。QUIC 每个 Stream 有独立滑动窗口，Stream 2 丢包不影响其他 Stream。

![QUIC 独立 Stream](https://cdn.xiaolincoding.com//picgo/image-20240105144623562.png)

**流量控制**：QUIC 有 Stream 级和 Connection 级两级流控，通过 `window_update` 通告可接收字节，通过 `BlockFrame` 通告被流控阻塞。接收窗口右边界在已收有序数据超过最大窗口一半时右移。

**拥塞控制**：QUIC 默认使用 Cubic，也支持 Reno、BBR 等；拥塞控制实现在应用层，可以随浏览器更新，也可以按应用配置。

**连接建立**：QUIC 内含 TLS 1.3，1 RTT 完成连接 ID 协商和密钥协商；会话恢复可以 0 RTT，应用数据与握手包一起发送。

**连接迁移**：QUIC 使用连接 ID 标识端点，而不是四元组。IP 或端口变化后，只要连接 ID、TLS 密钥等上下文仍在，就可以复用原连接。

### TCP 与 UDP 的端口

**TCP 和 UDP 可以使用同一个端口**。内核中 TCP 和 UDP 是独立模块，IP 头部的协议号决定交给哪个模块，端口号再区分应用。因此 TCP 80 和 UDP 80 可以同时存在。

**多个 TCP 服务进程绑定同一端口**：

- 同 IP + 同端口：报 `Address already in use`；
- IP 不同、端口相同：可以成功；
- `0.0.0.0:8888` 与 `192.168.1.100:8888` 冲突，因为 `0.0.0.0` 代表所有本地 IP；
- `SO_REUSEPORT`（Linux 3.9+）允许多个进程绑定同 IP + 同端口。

**重启服务报 Address already in use**：服务端主动关闭后留下 TIME_WAIT，该 IP + 端口仍被占用。`SO_REUSEADDR` 允许在 TIME_WAIT 存在时绑定，也允许绑定不完全相同的 IP。

**客户端端口复用**：`connect()` 从 `ip_local_port_range`（默认 32768–61000）选择端口。只要四元组不同，同一客户端端口可以连接不同服务端。客户端 TIME_WAIT 过多只影响同一目的 IP + 端口，换服务端仍可建立连接；`tcp_tw_reuse` 只对客户端且 TIME_WAIT 超过 1 秒生效。

### 总结

| 主题     | 关键结论                                                           |
| -------- | ------------------------------------------------------------------ |
| 连接建立 | 三次握手防止历史连接、同步 ISN、避免资源浪费                       |
| 连接断开 | 四次挥手保证双向关闭；TIME_WAIT 等待 2MSL                          |
| 可靠传输 | 超时重传、快速重传、SACK、D-SACK、滑动窗口、累计确认               |
| 流量控制 | 接收方窗口控制发送量；零窗口需要探测；Nagle 避免小包               |
| 拥塞控制 | 慢启动、拥塞避免、超时重传、快速重传与快速恢复                     |
| 性能优化 | 队列、TFO、窗口扩大、缓冲区、TIME_WAIT 与 Keepalive 参数           |
| 异常排查 | ISN、SYN 丢弃、Challenge ACK、乱序 FIN、崩溃/断电/拔网线、队列溢出 |
| TCP 边界 | 升级困难、握手延迟、队头阻塞、连接迁移成本                         |
| QUIC     | UDP 之上实现可靠传输、独立 Stream、1 RTT/0 RTT、连接 ID 迁移       |
| 端口     | TCP/UDP 端口独立；bind 冲突取决于 IP 和端口；客户端端口可复用      |

TCP 用大量机制换来了可靠传输，但这些机制也带来了握手延迟、队头阻塞和升级困难。QUIC 在 UDP 之上重建可靠传输，把连接管理、加密、流控和拥塞控制放进应用层，解决了 TCP 的部分结构性问题；但 UDP 在部分网络中被限制，QUIC 的部署和普及仍需要时间。
